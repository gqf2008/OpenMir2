## 2. 方法：怎么把 500 个假人分到多条 gate 线

`load_gate.ps1 -Port` 是**登录网关**端口（BotSrv `MShare.g_nGamePort` ⇒ `LoginScene` 首连 7000），
**不是游戏网关端口**。游戏网关端口由服务端在选角成功时下发的 `SM_STARTPLAY` 路由体决定
（Bot `SelectChrScene.ClientGetStartPlay` 解析 `sport\addr`）。

路由来源是 **DBSrv 的 `ServerInfo.txt`**（exe 同目录）：每行 `角色网关IP 游戏网关IP 端口[,端口…]`，
DBSrv 在每次 `CM_SELCHR` 时 `Random(GateCount)` 随机选一条（C# `UserService.GetGameGateRoute`；
Rust `bins/db-srv/src/route.rs` 逐行移植，`pick(usize::MAX)`）。因此：

- N=1：`127.0.0.1 127.0.0.1 7200`
- N=2：`127.0.0.1 127.0.0.1 7200,7201`
- N=4：`127.0.0.1 127.0.0.1 7200,7201,7202,7203`

这是**服务端随机分配**（生产里等价于「登录/选角层按负载或随机下发游戏网关」），
无需改代码、无需在数据面加代理；每档重启整栈（DBSrv 启动时读路由表）。
每端口实际分到的 bot 数由 DBSrv 的 Debug 行 `玩家获取游戏网关信息 RunGame:127.0.0.1 Port:720x`
逐条计数（N=2/4 轮次开启了该日志；N=1 无此日志，按构造 500 人全在 7200）。

**多线的正确形态是「一个 game-gate 进程的 N 个端点」**（现网 `E:/MirServer/RunGate/config.conf`
本身就是 `Count=3` + 7200/7201/7202 一个进程）。先试过「N 个单端点进程」，实测**不可用**：

- gate 的登录串里带 `service_id` = **端点下标**（`mir2-rs/bins/game-gate/src/lib.rs` 的
  `service_id: u8::try_from(i)`），N 个单端点进程每个都是 `service_id=0`；
- 于是所有会话都登记到 game-svr 的 0 号线，1 号线的下行帧全部落到 0 号线的槽表里找不到
  （实测 N=2 首轮：102,732 条 `下发 SM_* 帧时 socket=N 的槽不存在`，`in_world` 241/500）；
- 单进程 N 端点时每个端点各有独立连接、独立 `SendChecked`/队列，服务端按线号路由，
  才是与 `GATE_SLOT_CAPACITY=20` 对应的并发形态。

三档拓扑因此是 `Count=1/2/4` 的一个 game-gate 进程（端口 7200；7200-7201；7200-7203），
每档重启整栈；game-svr 侧 `分配线号` 日志确认 N 条连接分别拿到 0..N-1 号线。

窗口：`HoldSec=60`。按 A4 口径 `60s < 360s` 只算冒烟，不是结论级窗口；
本实验三档用**同一窗口**横向对比，且每档 `in_world` 在窗口末已平台（§3），
60s 末值可比较「平台高低」，但不能单独当生产容量结论。

## 4. A6 均衡度：线数不等于并发

**bot 分摊是均衡的**：N=4 两次分别 128/108/140/124、129/121/117/133（最大/最小 1.30、1.14）；
N=2 为 280/220（1.27）。随机路由没有系统性偏置。

**帧负载严重不均**（这正是 A6 要打折的）：
- N=2：帧占比 81.3% / 18.7%，而 bot 占比 56% / 44%；bottleneck 线 = 7200（overflow 59%）。
- N=4 #1：帧占比 **3.4%–40.7%**（bot 21.6%–28.0%）；7201 几乎空闲（overflow 0），
  7202 扛 40.7%。
- N=4 #2：帧占比 **5.2%–46.7%**；这次空闲线换成了 7202（overflow 0），7200 扛 46.7%。

**瓶颈线每次不同 = 拥塞级联，不是某条线固定故障**。证据链：
1. 空闲线的 `overflow=0`、`rejected_sessions=0`、`max_depth` 未打满（4070 / 3131）；
   拥塞线全部 `max_depth=4096`、overflow 占 hold 的 53–70%、`timeout_flush` 67–82 次。
2. 拥塞线的 `hold/bot` 是空闲线的 5–9 倍（N=4 #1：3,283–4,780 vs 518；
   N=4 #2：3,732–4,866 vs 602）——若只是 bot 数差异，应只差 ~10–20%。
3. 空闲线在两轮 N=4 之间从 7201 换成 7202，而 bot 分摊两轮相近 ⇒ 触发因素是
   “哪条线先被队列打满”的时序，而不是分配方式。
4. 环路的机制（本批 A+B 二进制）：队列满 ⇒ `overflow` ⇒ 对会话发 `GM_CLOSE`（`rejected_sessions`）
   ⇒ 该线会话/登录流量进入更激烈的重试/重建，进一步维持队列满；未打满的线则一直走
   `queued→flushed` 的快路径（`overflow=0`）。这就是为什么总帧量随线数放大：多一条线
   就多一个可能进入级联的队列，而级联本身会放大流量。

**对结论的影响**：`N=4` 的延迟改善部分来自“恰好有 1 条线空闲”的分配（空闲线把
一部分 bot 的 tick 拉低），但 4 条线并没有提供 4 份可用的 `SendChecked` 并发；
按 A6 口径，「4 线有效」的结论要打折。生产上若采用多线，必须：
(a) 按**实测负载**而不是按 bot 数分配；(b) 队列策略不能让溢出引发关会话的正反馈
（即关键性卡的方向）；(c) 每线独立观测（本卡采集的 `gate=` 维度）。

## 5. 判据结论（写死口径）

- 判据：N=4 时 `in_world ≥ 490` **且** `≥201ms 占比 < 5%`。
- 实测：N=4 #1 = 483 / 3.1%；N=4 #2 = 467 / 1.0%。
- **两次都不满足**（in_world 分别差 7 和 23 人）。按卡面规则：
  **单线瓶颈不能只用部署拓扑解决，转 `openmir2-gateway-throughput-pipeline`。**

补充（不改变判据结论）：
1. 延迟面已经达标且余量很大（1.0–3.1% vs 5% 阈值），多线**确实**缓解了单线 `SendChecked`
   饱和；进世界面的缺口更像是**入世界前的关键帧被队列溢出/关会话吃掉**（A+B 二进制的
   overflow→GM_CLOSE 行为，且该卡总监裁决“暂不合并”）。因此下一步的吞吐提升应走
   关键性/流水线方向，而不是继续加线。
2. 本实验窗口 60s 是冒烟级（A4：<360s 不得作为压测 GREEN 结论）。`in_world` 在窗口末已平台，
   但**结论级（360s）窗口未跑**；若要把“部署路线是否够”写成最终结论，需要再开一次 360s 窗口。

## 6. 生产可行性（A4）

- **不改客户端协议**：多线只改服务端拓扑（game-gate 进程的 `Count`/`GatePortN`）与选角路由
  （DBSrv `ServerInfo.txt`）。客户端仍是一个“游戏网关地址:端口”。
- **可行形态**：一个 game-gate 进程 N 个端点（现网 Count=3 的形态），game-svr 每个端点一条
  连接、一个槽位（`GATE_SLOT_CAPACITY=20` 给出 20 线上限）。
- **不可行形态**：N 个单端点进程。`service_id` 取端点下标 ⇒ 全部登记 0 号线
  （实测 102,732 条槽不存在、in_world 腰斩）。若生产要“多进程”，必须先修
  `service_id` 的来源（服务端分配的线号），那是代码改动，不在本卡内。
- **路由**：当前用随机分配；生产建议按实测负载分配并保持**会话粘性**（一个会话不能中途换线）。
- **风险**：本批实测多线会把“发送尝试/溢出”总量放大 4–5 倍（拥塞级联），每线需要独立
  背压观测与告警；叠加 20 线上限，线数不是免费容量。
- **成本**：每线多一个端点连接与队列状态（内存很小）；主要成本是运维复杂度与不均衡风险。
