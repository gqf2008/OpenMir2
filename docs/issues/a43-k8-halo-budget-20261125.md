## 1. Q1：每区带内实体与 `MIR2_MAX_HALO_BAND_ENTITIES=512`

### 1.1 公式与校准

`snapshot_border` 按 `border_contains`/`within_distance` 取「rect 内 + 距 rect ≤ halo」的实体 ⇒ 每个条带的取数环 = `(W+24)×700 − (W−24)×676`（y 两侧是地图边界，不外扩），再按实体密度折算。用 K=4/1000 的实测（h=321）校准密度因子 **0.877**（玩家/怪物向中心聚，非均匀）。

校准结果：K=4、1,000 人 ⇒ 预测 321，实测 321/325/333 ✓。

### 1.2 三档预测

| 人数 P | 地图实体总数（3,820+P） | K=4 环占比 6.66% ⇒ h/区 | K=8 环占比 6.29% ⇒ h/区 |

### 1.3 结论（要分清「启动门」与「live 带」）

- **启动门不会撞**：`check_band_gate` 在 tick 0 跑，此时 5,000 个 bot 都在各区 3 个落点上（离条带边 ≥43 格，远于 halo 12），带内只有静态 **3,820** ⇒ K=8 每区 ≈**240**、K=4 ≈**254**，三档（2000/4000/5000）都 < 512。**K=8 在 2000/4000/5000 三档都不撞门。**
- **live 带会超**（玩家散开后）：K=8 大约在 **4,300 人**越过 512（5,000 时 554，超 8%）；K=4 大约在 **3,900 人**越过（5,000 时 587，超 15%）。
- **超 512 不会启动失败**：512 只是启动期代理指标，运行期没有任何门按它判红；超了只把镜像成本抬高（见 §2）。⇒ 若按「门」问，答案是「不撞」；若按「设计裕度」问，K=8 在 5,000 档只剩 8% 裕度，K=4 已经负。

## 2. Q2：镜像成本模型与「4 区 / 8 区」

### 2.1 模型

- `await_neighbors`（`region_loop.rs`）每 tick 读**其余全部区**的快照；`apply_mirrors` 把各邻区实体 flat 后**排序**（同格序）。
- 每区每 tick 的排序量 `S = (K−1) × h`；实测 `HostMirrorApply = 0.978 ms` 对应 K=4 的 `S = 3×325 = 975` ⇒ **≈1.0 µs/实体**（含排序）。
- `HostHaloSnapshot` 与 K 无关（每区只扫自己的 span）：K=4 实测 0.730 ms。

| 人数 | K=4：S / MirrorApply | K=8：S / MirrorApply |
| --- | --- | --- |
| 2,000 | 1,163 / ≈1.2 ms | 2,561 / ≈2.6 ms |
| 4,000 | 1,562 / ≈1.6 ms | 3,441 / ≈3.4 ms |
| 5,000 | 1,762 / ≈1.8 ms | 3,881 / ≈**3.9–4.5 ms** |

（8 区的 S 还要乘 `log S` 的轻微放大，取 1.15×。）

### 2.2 结论

- **镜像不是瓶颈**：K=8/5,000 每区 ≈4.5 ms/tick，占 200 ms 窗口 2.2%；8 个区线程并行，宿主那一路只多 4.5 ms。
- 但它是**唯一随 K 二次增长**的段（总 CPU = K×(K−1)×h）；K=16 时同口径约 **8–9 ms/区**，仍可接受，真正随 K 线性上涨的是线程数与 barrier 参与方（见 §4）。
- **5,000 档选 8 区**，理由是**每区玩家数**，不是 halo：
  - 宿主条带留空 ⇒ K=4 的 3 条数据带 = **1,667 人/区**；K=8 的 7 条 = **714 人/区**。
  - 总监消息里的「1250/区」「625/区」是「宿主条带也吃人」的算法，与「宿主 0 人」的前提冲突；按后者算，8 区把每区负荷降到 4 区的 **43%**。
  - halo 一侧 8 区也略好（554 vs 587），但不是决定项。

## 3. Q3：区 0 的 1×1 span —— **不需要**

- `from_zone_spans`（`zone.rs`）会给**「一个 span 都没写」的整张图**补一条 `default_zone` 整图 span；本 run 注册表 320+ 张图 ⇒ 区 0 自动拥有 320+ 个整图 span ⇒ `EmptyZone(0)` 永不触发，「每区至少一个 span」的约束已满足。
- ⇒ K=8 布局**可以**把 map "0" 完整切给区 1..8，区 0 在 map "0" 上留 0 个 span；`decide_login_landing` 于是不可能返回 `HostZone`（落点必命中某条带），宿主自然 0 人。
- **若仍要坚持留 1×1**（例如为了「区 0 至少在 map 0 上有身份」）：只能从某条带切一格，例 `0:0=0,0-0,0` + 区 1 改为 `1:0=1,0-87,699`（面积和仍等于图面积、无重叠 ⇒ 合法）。**不推荐**：会给宿主造一个落点（倒霉玩家落宿主）+ map 0 上一条 halo 交互，收益为零。
- 注意：`layout-map0-8z.json` 现在 **zone 0 拥有 x 0..87**（87 宽条带）。要「宿主 0 人」，要么按 K=4 的做法靠 placement 避开（`hostish=0`），要么把这条带改给 zone 1（并给 zone 1..7 重新均分 700 格）。后者更省心：宿主连这条带的世界都不用算。

## 4. 真正的瓶颈（与 Q1/Q2 无关，但必须同时报）

- **10 ms/tick 的执行预算**：`ZoneDrainLimits::PRODUCTION`（`lib.rs`）= `execute_wall: 10ms`、`execute_check_every: 16` ⇒ 每区每 tick 只执行约 **47 条**（实测 drain 47.4/tick，`carry ≈ drain`、`budget_hit` 1,783/1,831 即几乎每 tick 触顶）。
- **barrier 等待占了大头**：区 tick work 199 ms 里，`HostWorldTail` 198.5 ms、探针合计仅 ~0.5 ms；barrier（两道之和）p50 **159 ms**，`sleep=0.000` ⇒ 尾段计算 ≈ **39 ms**，其余是等待。
- ⇒ 两种互斥解释必须先用一次测量分清：
  1. **等待是真空闲**（等对端发布/等节拍）⇒ 把 `execute_wall` 抬到 40–60 ms 可把每区吞吐抬 4–6×，这是 5,000 档最直接的一刀；
  2. **等待被 CPU 抢占/真实串行**（4–8 个 zone 线程 + 宿主 + gate + db-srv 抢核）⇒ 抬预算只会拉长 tick，必须减核上负载或减单条成本。
- 无论哪种，**5000 档按现状都不够**：K=8/714 人/区，按 334 人 ⇒ 128 条/tick 的需求比，714 人 ⇒ ≈274 条/tick，而排水仍 ≈47 条/tick ⇒ 仍丢 ~70%。

## 5. 三行结论

1. **K=8 在 2000/4000/5000 三档都不撞 `MIR2_MAX_HALO_BAND_ENTITIES=512`**（tick 0 只算静态 ⇒ 每区 ≈240）；但「live 带」在 ~4,300 人越过 512（5,000 时 554），运行期无门，只抬镜像。
2. **5,000 档选 8 区**：每数据区 714 人（K=4 = 1,667），镜像 ≈4.5 ms/区/tick（窗口 2.2%）、halo 快照 ≈0.7 ms；O(K²) 只在 K=16 才值得再优化。
3. **4/8 都不是当前的主要矛盾**：K=4/1000 已丢 39.2 万条（~65%），根因是 LOCAL 段 **10 ms/tick** 执行预算，叠着 **159 ms 未解释的 barrier 等待**。下一步先测清这 159 ms 的归属（barrier1/barrier2 分开记 + 各区发布时刻），再决定抬预算还是减单条成本；区数扩容不解决丢包。
