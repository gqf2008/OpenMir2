# 扇出成本拆解（refmsg fanout，2026-11-22）

> 输入（今晚 release 实测，`opc-19` 提供）：2000 在线（in_world 1973）时 tick **p99 201ms / p90 125ms**；
> 每 tick `refmsg_targets` **均值 88,567**；`max_single_event_us` p95 **2.48ms**；`budget_hit 100%`。
> ⇒ 成本不在单个事件，而在**每个收件人目标的帧处理**。
>
> 只读分析：未改产品代码、未构建。每段标注 **读代码 / 实测 / 估算**。

## 1. 每条目标帧做了什么（读代码）

路径：`broadcast_ref_msg_opt` / `broadcast_ref_msg_from_walk_candidates` → **`send_ref_msg_to_targets`**
（`mir2-rs/bins/game-svr/src/lib.rs` 的 `send_ref_msg_to_targets`，入口 18176，函数 18186）。

逐目标循环体（原文顺序）：

| # | 动作 | 成本类型 | 说明 |
| - | --- | --- | --- |
| 1 | `include_self` 门 | 分支 | 跳过发送者自己（可选） |
| 2 | `online.find_by_actor(target_id)` | **哈希查表** | 每目标一次 actor→`OnlineEntry` 查找 |
| 3 | `route_to_gate(gates, gate_idx, socket, …)` | **哈希查表 + 有效性判定** | 每目标一次 gate 线号→通道查找 |
| 4 | `for body in bodies { body.clone() }` | **堆分配 + memcpy（每 body 一次）** | **核心扇出成本**：同一帧对每个目标复制一份 `Vec<u8>` |
| 5 | `tx.send(SimToGate::SendFrame { socket, body })` | **无界 mpsc 入队（含节点分配）** | 每目标每 body 一次消息入队 |

下游：网关线程 `gate_conn` 侧按 `send_gate_msg` 规则出队 → 网关线发送队列（有界 256KiB/4096 帧）→ `SendSocket`。

**结论（读代码）**：3 次分配/查表 + 2 次哈希 + 1 次克隆/目标/体。克隆与入队是 O(目标数)，与"事件数"无关
——这正是 `refmsg_targets` 比 `refmsg_calls` 更能解释 tick 成本的原因。

## 2. 成本结构估计（估算，除非另标）

- 每 tick 目标数 **88,567**（实测，均值）。
- 每目标可用时间（把整轮预算全算给扇出）：
  - p99 201ms ⇒ `201,000µs / 88,567 ≈ **2.27µs/目标**`
  - p90 125ms ⇒ `125,000µs / 88,567 ≈ **1.41µs/目标**`
- 单事件 p95 2.48ms（实测）说明"一次事件"（含其内部全部扇出）并不便宜——
  单事件成本 = 目标数 × 每目标成本 + 事件自身计算。
- **每目标 1.4–2.3µs 是"整轮只做扇出"的上限**；实际还要分摊世界 tick/入站/DB，
  真实可用更低，故 2000 档的扇出已接近**该档的预算上限**（估算）。

## 3. 三条可降的路（收益/风险/与 L2 切区的关系）

### ① 同帧多目标共享序列化（一次编码、多次发送）

- **做法**：`bodies` 已由调用方预先编码（读代码：`send_ref_msg_to_targets` 接收 `&[Vec<u8>]`，
  编码在调用方完成）⇒ **序列化已经共享**；真正可省的只剩 **每个目标的 `body.clone()`**。
- **收益（估算）**：省掉 88.5k 次 `Vec<u8>` 分配+拷贝。若单次 clone ≈0.15–0.4µs（量级估计），
  合计 **13–35ms/tick**，即 p99 201ms 的 **6–17%**。改成 `Arc<[u8]>` 或"共享缓冲 + 引用计数"可拿到上限。
- **风险**：`SimToGate::SendFrame` 变 `Arc` 会波及网关侧写路径；需保证跨线复用缓冲不被就地改写。
- **与 L2 切区**：**正交**——任何切法都需要把同样的帧发给同样的收件人，这条单独有效。

### ② AOI 结果缓存（同一 tick 内多个广播复用可见集）

- **做法**：同一 actor 在同一 tick 内可能被多次 `SendRefMsg` 扫可见集；缓存 `(actor, x, y, tick)` → 收件人集合。
- **收益（估算）**：取决于"同 tick 内重复扫描比例"——**无实测**；若重复率 30–50%，
  省 **26k–44k 目标/轮** ⇒ p99 降 **30–50ms**（估算区间）。
- **风险**：可见集在 tick 内因移动/隐身变化 ⇒ 缓存必须带位置/状态指纹，否则错误收件人。
- **与 L2 切区**：**正交**（缓存键可加"区"维度，切区后仍成立）。

### ③ 减少广播源（合并同 tick 同类帧）

- **做法**：同 tick 同 actor 的同类 17/638 等合并为一条（收件人集合并集）。
- **收益（估算）**：只对"同源同帧"有效，需先量"重复 (actor,ident)/tick 比例"——**无实测**；
  乐观情形 p99 降 10–25%（估算）。
- **风险**：会改变客户端可见帧数（**可能触犯"帧面等价"契约**），必须逐条对照 oracle 行为。
- **与 L2 切区**：**正交但收益被切区放大**——切区后每片目标数变少，③的绝对省时同比缩小。

> 哪条**只有切区才有效**：没有。三条都正交；L2 切区的价值是把 88.5k 目标**横向摊到多线程**，
> 而不是减少单目标成本。⇒ **切区不能替代 ①②③**，①②③也不能替代切区。

## 4. 判据（可证伪，全部标估算）

| 方案 | 预计 p99（2000 档） | 证伪条件 |
| --- | --- | --- |
| 现状 | 201ms（实测） | — |
| ① 共享缓冲（去 clone） | **165–190ms** | 实测 p99 仍在 ≥195ms |
| ② AOI 缓存（重复率 30–50%） | **150–170ms** | 实测 >180ms ⇒ 重复率远低于 30% |
| ①② 同做 | **130–160ms** | 实测 >170ms |
| ②+③ 激进 | **110–150ms** | 实测 >160ms（且需先过帧面等价） |

**验证方法**（任一方案）：同参数 2000 档跑 `refmsg_targets`/tick、`host_prof` 的 `HostFrames`/`HostInbound` 分段、
tick p50/p90/p99；对比表必须同时给"目标数没变"（证明省的是每目标成本）与"tick 降了"。

## 5. 什么都不做的硬上限

- **入队速率**：88,567 目标/tick × 5 tick/s ≈ **44 万次 mpsc send/s**（估算，目标均值为实测）
  ⇒ 单轮 88.5k 个 `SendFrame` 入队 + 等量 `Vec` 克隆；内存分配器与通道节点分配是首要瓶颈（估算）。
- **每目标预算已到 1.4–2.3µs**（估算，见 §2）：在这个量级上，任何"每目标再发生一次分配"都会
  吃掉 10–25% 预算 ⇒ **不做的"上限"其实就是当前实现**：clone + 入队两次分配/目标。
- **socket 写次数**：网关侧每帧一次写；88.5k 帧/tick ⇒ 44 万写/s（估算）。TCP 聚合会缓解，
  但**用户态写系统调用**本身接近该量级的常态上限；再翻倍（1 万档）应先做 ①②。
- **结论（估算）**：2000 档尚未撞"物理硬上限"，但已撞**当前实现的上限**；不优化时，
  4000 档的扇出成本会线性翻倍（~90ms 的扇出段），叠加其他段即超 200ms 预算。
