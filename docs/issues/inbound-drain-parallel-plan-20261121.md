### 1.1 345/s 是哪一段

**就是第 5 段**：`sim_loop` 每轮 `EventDrain::begin(EventDrainBudget::PRODUCTION)` 的排水速率。

- `EventDrainBudget::PRODUCTION` = `max_events: 2000`、`max_wall: 50ms` `[读代码]`。
- 通道本身**没有限速**（无界 std mpsc）⇒ 到达速率不受控；**唯一的节流器是排水预算** `[读代码]`。
- w35 实测：`drain_events_drained = 124,211`（÷360s ≈ **345/s**）、`frames_in = 1,194,705`（÷360s ≈ **3319/s**）
  `[实测/摘抄：w35 归档的 `ENTRY_TELEMETRY` 原始计数器]`；积压 `≈1.07M` 是**两计数器相减的推算值**，
  不是队列实测长度（通道没有 gauge）`[推算]`。
- **单条事件处理成本无原始测量** `[无原始测量]`。已知的只有两个端点：
  - 若窗口内平均 tick ≈ 5 轮/s（200ms 名义值），50ms 预算/轮 ⇒ 250ms 排水墙钟/s ⇒ 反推 ≈0.72ms/条；
  - 但 w37 显示同一压力下 tick 已涨到 513ms `[实测/摘抄：w37]`，tick 数实际更少 ⇒ 该反推**偏小**，
    真实单条成本可能更高，也就是说「提高预算就能吃下 3319/s」**不成立**——文档 §5.1 记录：墙钟阀开到整轮
    200ms（4–5 倍）也只有 ~1.4k/s `[摘抄；原文未给公式，属推算结论]`。
- `drain_budget_hit = 1671` `[实测/摘抄：w35]`：**预算不是根因**，是「为保 tick 而截断」的症状。
  随之引用的「1671 / 3150 轮」里的 `3150` 与本文件的 `w35` 计数器**不是同一口径**，
  `3150 轮 / 360s ≈ 8.75 轮/s` 与「tick=200ms ⇒ 5 轮/s」**互相矛盾** ⇒ 该「轮」计数器的定义
  **未核到** `[无原始测量]`，引用时不要拿它与 tick 数互算。

### 1.2 结构性结论

1. **单消费者**：`GateEvent` 的两条通道只有一个消费者（sim 线程），而 sim 线程同时承担 `World` 的全部 tick 工作
   ⇒ 入站吞吐与世界计算**共享同一个线程的时间预算** `[读代码]`。
2. **无界 + 无读数**：普通通道无界且没有长度 gauge ⇒ 积压只能「到达 − 排水」离线推算；
   1.07M 是**推算值**，不是队列实测长度 `[推算]`。
3. **优先级只解决饿死、不解决吞吐**：优先通道（控制/进入）与反饥饿上限（`max_events/2`）
   只保证控制事件不被命令洪流淹死 `[读代码]`；对总吞吐没有贡献。

## 2. 并行化切分点

### 2.1 可切的维度与代价

| 维度 | 能否保「同一收件人帧序」 | 代价 / 风险 |
| --- | --- | --- |
| **每区（region）一队列 + 一 owner 线程** | **能**：同一区的所有事件仍由该区唯一 owner 按 FIFO 处理；跨区效果按合并键投到收件人所在区 | 需要「会话 → 区」映射与过区 handoff 的一致性（§4）；区之间交互顺序需要全局键 |
| 每网关线一队列 | **不能**：同图玩家分属不同网关线，A 打 B 与 B 的命令会并发乱序 | 只适合做「入队前的纯解析并行」，不能做事件体并行 |
| 每连接（socket）一队列 | **不能**：同上，且单玩家相邻帧会给不同 worker | 仅适合解析；不解决 3319/s 的处理成本 |
| 单 World 内 bevy 多线程执行器（L1） | 取决于系统依赖图；**未实测** | 只降单 tick 墙钟，不改入站吞吐；且必须先过重放确定性门 |

### 2.2 推荐切法（与拆区设计同构）

- **N 个区**（`docs/map-zone-split-design-20261122.md` 的 N=10–12）：每区 = 一个 `World` + **一条入站队列** + **一个 owner 线程**。
- **T 个 worker 线程**（T≈8–10）：每线程顺序服务若干区（一区同时只被一个线程持有）。
- 入站事件在**入队时**就被路由到某个区队列；区 owner 线程按 FIFO 处理本区事件，语义与今天「单线程按到达序处理」在该区内部**完全一致**。

### 2.3 「同一收件人帧序」怎么保

三条不变式（设计约束，不是实现）：

1. **区归属唯一**：任一时刻，一个角色只属于一个区；其所有「会影响它」的事件都在该区队列里处理。
2. **区内 FIFO**：区内事件按到达序处理（沿用今天的 `std mpsc` FIFO 语义）。
3. **跨区效果显式化**：任何跨区效果（跨区可见广播、行会/全服消息、跨区攻击）不直接写对方 `World`，
   而是**投到收件人所在区的队列**，并携带全局排序键 `(tick, region_id, seq)`（沿用拆区设计 §Q3 的合并键）。
   收件人侧按该键有序合并 ⇒ 相对顺序与「不拆」一致。

**全服广播**（`SM_SYSMESSAGE`/行会公告等）在拆区设计里已定为「合并键 + 收件人侧有序合并」；
本设计的补充是：**广播的扇出发生在收件人所在区/网关线，而不是发送者区**，否则发送者区会被扇出成本压住。

### 2.4 不能并行化的部分（必须承认）

- 同一区内的 `World::tick` 仍是单线程（除非 L1 实测通过重放确定性门）。
- 全局唯一序列发生器（若采用）会成为热点：用**分段批号**（每区预领一段 seq）而不是全局原子自增，
  否则 3319/s 下每帧一次 CAS 会把并行收益吃掉大半。

## 3. 背压

### 3.1 现状

- 入站通道：**无界、无丢弃、无长度读数** `[读代码]` ⇒ 生产快于消费时内存线性增长。
  1.07M 事件 ≈ 150–250MB `[推算：文档 §5.2 的 150–250B/条 × 积压条数]`；10000 档外推 2.5–3M ≈ 0.4–0.8GB
  `[推算]` ⇒ **OOM 风险**。
- 下行已有可抄的样板：`gate_queue::PendingQueue` 有界（帧数/字节双阀）+ `gate_backpressure::DropStats`
  逐类计数 + NDJSON 落盘 `[读代码]`。

### 3.2 设计口径

1. **每条入站队列有界**（按帧数与字节双阀，与下行同口径）。上限不是拍脑袋：按「单条成本 × 队列长度
   ≤ 允许的最大积压延迟」定，例如目标「排队延迟 ≤ 2s」。
2. **分级丢弃**（从最可牺牲到最不可牺牲）：

   | 级别 | 事件类 | 规则 |
   | --- | --- | --- |
   | P0 永不丢 | 控制（`Closed`/`RegisterGate`/`UnregisterGate`/`KickAccount`）、进入（`LoadDbRequest`）、admin | 独立优先通道；任何负载下丢弃计数必须为 0 |
   | P1 不可丢 | 登录/认证/角色操作类命令 | 溢出时**先饿普通命令**，不丢这些 |
   | P2 可合并 | 移动类命令（同会话保留最新一条） | 溢出时按会话合并（丢旧留新），计数 |
   | P3 可丢 | 高频战斗/心跳类 | 溢出时丢最旧，**按会话限频**，计数 |

3. **丢弃必须有可观测面**（否则等于静默丢数据）：
   - 每区 `inbound_queue_depth`、`inbound_queue_bytes`（gauge，每 tick 采样）；
   - 每类 `inbound_dropped{class,zone}`、`inbound_coalesced{zone}`；
   - 每轮 `inbound_drain_events`、`inbound_drain_wall_ms`、`inbound_overload_ms`；
   - 汇总行 + NDJSON（复用 `gate_backpressure` 的落盘方式），并进 `ENTRY_TELEMETRY`。
4. **守恒恒等式**（每采样窗口断言）：
   `enqueued = drained + dropped + coalesced_dropped + pending`，且 `pending` 来自 gauge 而不是推算。
5. **生产侧背压（可选，需单独评估）**：队列超 HWM 时可以「暂停读该网关线」把压力推回 TCP 内核缓冲；
   代价是**整条网关线所有会话一起卡住**（当前一条线复用多会话）。默认不做，只做丢弃 + 计数。

## 4. 与拆区的关系

- **分区键 = 会话当前所在区**。今天的 `GateEvent` 只带 `index`/`chr_name`/`socket`，**不带区号** `[读代码]`
  ⇒ 入队前需要一次「会话 → 区」查表（路由层），并在过区 handoff 时**原子切换**该映射。
- **过区 handoff** 沿用拆区设计：源区冻结 → 序列化最小状态 → 目标区下一 tick 插入 → 源区发离开、目标区发进入。
  入站侧新增一条约束：**handoff 完成前后，该会话的事件只能进一个队列**（旧区或新区，不能两边）；
  两边都进 = 重复处理，两边都不进 = 丢命令。
- **跨区消息**：投递到收件人所在区，带 `(tick, region_id, seq)`；同 tick 内跨区偏差 ≤1 tick（拆区设计 §Q4）。
- **与跨进程分片（`shard::ShardRuntime`）的关系**：分片是**进程级**（哪台机器拥有哪张图），
  区是**进程内**（哪条队列/线程拥有哪张图的一片）。两者正交：分片先决定「这张图归谁」，
  区内并行决定「归谁之后怎么并行排水」。

## 6. 验收断言（都可机判）

### 6.1 不丢 / 不重

- **A1 守恒**：任意采样窗口，每个区
  `enqueued == drained + dropped{all classes} + pending`。
  断言写法：gauge 与计数器每个窗口做一次等式判定，偏差 > 0 ⇒ RED（并打印四项原值）。
- **A2 端到端不丢**：沿用现有对拍装置——同一场景（N=1 单区）与拆分后（N=区数）各跑一遍，
  **逐收件人帧序列逐字节相同**（不是「条数相同」）。拆区设计 §Q3 的合并键乱序注入测试是它的加强版。

### 6.2 不乱序

- **A3 逐收件人有序**：对每个收件人，帧序列与单线程参考实现**完全相同**（包括 `series`/`due_ms_rel`）。
- **A4 合并键乱序注入**：人为打乱到达序但保留 `(tick, region_id, seq)` ⇒ 输出仍按该键有序。
- **A5 交叉交互顺序**：构造 A 打 B、同时 B 移动的场景，拆分后与 N=1 的帧序列一致；
  不一致 ⇒ 说明跨区/跨线程顺序没被键约束住。

### 6.3 背压可观测

- **A6 溢出可证**：灌入 `> HWM` 的事件流，断言 `inbound_dropped > 0` **且** `inbound_dropped{P0} == 0`
  （控制/进入永不丢）。
- **A7 合并可证**：对 P2 类按会话连发 N 条移动，断言 `inbound_coalesced == N-1` 且最终位置等于最后一条。
- **A8 有界**：`inbound_queue_depth ≤ HWM + 1` 在每个采样点成立（允许 1 条周转）。

### 6.4 性能与回归

- **A9 tick 预算**：5000 档同参数（`frames_in ≈ 3319/s`）下 `tick P99 ≤ 200ms`，且
  `入队→处理` 延迟 p90 从 w35 的 85s 回到秒级（与 §5.1b 的验收判据一致）。
- **A10 确定性**：同 N / 同种子 / 同输入两次运行**逐字节相同**（重放确定性门，拆区设计 §Q5 同一判据）。
- **A11 零回归**：现有 `cargo test --workspace` 与对拍全量门上红集为空（按项目合并门 §3）。

## 7. 结论（可施工顺序）

1. **先量 M1 + M7**（零语义改动）：给入站通道加 gauge、做「假消费者」吞吐压测。
   这两项不做，后面所有并行化数字都是推算。
2. **再上分区骨架**：N 区 × T 线程 × 每区一队列；先保持**单线程处理**（每区一个队列、共用一个 worker）
   验证 A1/A2/A3 守恒与顺序，再逐区放开到多 worker。
3. **背压与丢弃**按 §3 分级实现，先只加计数不丢弃，确认计数面能对上 w35 的推算（1.07M 量级）。
4. **最后才谈 L1**（区内 bevy 多线程），且必须先过 A10。

> 一句话：**345/s 不是「调大预算」能解决的（文档 §5.1 实测 4–5 倍预算仍只有 ~1.4k/s），
> 也不是「拆 World」自动解决的（拆了 World 但共用一条入站队列 = 不变）。
> 必须先有「每区一队列 + 并行排水」，才谈得上 3319/s。**
