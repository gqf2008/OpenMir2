# 500 档容量结论（2026-11-16 定稿草案）

> 状态：**草案**（供内部评审，未作为对外文件发布）。每个数字后注明「怎么测的 / 哪一轮 / 哪个归档」。

## 0. 一句话结论

在 **500 并发**、Rust `game-svr` 单进程单线程、500 个 bot 同图的条件下：
**窗口可判 GREEN、零异常；P1 优化（master `e768b9fd3`）带来同口径 `HostInbound` −45.4%、工作段 −34.6%；
诊断门（profile 主门 / `SLOW_MS` 快照）没有可分离的尾部代价**。

## 1. 500 档 GREEN 的三轮证据

| 轮次 | 树 | 归档 | 结果 |
| --- | --- | --- | --- |
| 判据轮 | `c74b4ce42` | `E:/UserFleet/load-360-recvnull-verify-20261116/` | `verdict=GREEN / rc=0 / in_world=500/500 / internal_errors=0` |
| 分离轮 A（profile 主门开、`SLOW_MS` 未设） | `57a0c9f12` | `E:/UserFleet/load-360-slowsep-A-20261116/` | 同上 |
| 分离轮 B（主门 + `SLOW_MS=50`） | `57a0c9f12` | `E:/UserFleet/load-360-slowsep-B-20261116/` | 同上 |

- 三轮均为 **`HoldSec=360`、`conclusion_valid=true`、`recv_packet_null=0`、`error_census` 全部 fault 类别为 0**；
  归档 `artifacts.sha256.json` 各自 **7/7 匹配**（.NET SHA-256 生成，`verify_artifacts.py` 校验）。
- 每轮都是**新栈**（每轮起栈 → 跑满 360s → 收栈），未复用栈进程。

## 2. P1 优化的同口径收益

**口径**：只取「`in_world=500` 之后、剔除收尾 shutdown-drain 块」的稳态 50-tick 块，按块均值平均。

| 轮次 | 工作段 ms/tick | `HostInbound` ms/tick | 每客户端 inbound ms | 稳态实体均值 |
| --- | --- | --- | --- | --- |
| baseline（11-15，`262a95855` 树） | 76.58 | 54.50 | 0.1090 | 4,949 |
| P1 后（W2，`c74b4ce42`） | 50.11 | 29.73 | 0.0595 | 5,645 |

⇒ **工作段 −34.6%、`HostInbound` −45.4%、每客户端 −45.4%**。

**作废的旧数**：11-16 早先报的「工作段 −59.15% / `HostInbound` −77.31%」是**空载稀释**的粗数
（W1 的「实体 ≥490」稳态选择把 BotSrv 启动前约 163s 空载算进窗口；日志实证 BotSrv 02:42:11 启动，
而 02:39:28 已 entities=747）。**该两个数字不得对外引用。**

## 3. 诊断代价：无可分离代价

同树 `57a0c9f12`、同档 500、各 360s、每轮新栈的两轮：

| 指标 | A（`MIR2_TICK_PROFILE=1`，`SLOW_MS` 未设） | B（再设 `SLOW_MS=50`） |
| --- | --- | --- |
| tick P50/P90/P99/max | 16 / 32 / 47 / **78** ms | 16 / 32 / 47 / **187** ms |
| ≥201ms 次数 / 占比 | **0 / 213,224** | **0 / 210,597** |
| 工作段 | 43.71 ms | 45.47 ms（+1.77，+4.0%） |
| `HostInbound` | 24.89 ms | 26.76 ms（+1.87，+7.5%） |

- 分位完全相同、两轮都无 ≥201ms 样本；点估计差值与轮内方差**不可分离**（z≈0.95 / 1.31）。
- 早前 W2 的 profile 轮曾出现尾部（P99 62 / max 375 / 58 次 ≥201ms）；**本轮 A 同形态未复现（47/78/0）**
  ⇒ 该尾部**不是诊断门的稳定代价**；**其成因未定位，不排除偶发**。
  本结论**只排除「系统性代价」**，不对那一次做原因断言。

## 4. 唯一可测的代价：快照输出量（可选优化，未做）

B 轮的慢 tick 快照：**430 行 / 1.91MB**，平均 **4.4KB/行**、最大 **59KB/行**，平均 **125 个 probe 行/行**、最大 **1,835**。
原因是**每调用一行、未按 probe 名聚合**。这解释了 B 轮 CPU 峰 80% vs A 轮 62%，以及一次 187ms tick。

**建议（可选，未实现）**：把同一 tick 内同名 probe 行**按名聚合成一行**（次数 + 总 ms）。
按当前行数比 **125:1** 推算，输出量**有望下降 1–2 个数量级**；实际幅度取决于聚合后仍需保留的字段，
**未实测**。**此优化未做，不影响上述任何结论。**

## 5. `hear_targets_at`：已从主体降为次要项

- 探针：master `57a0c9f12`（`MIR2_TICK_PROFILE_SLOW_MS` 打开时，慢 tick 快照里出现
  `| probes hear_targets_at=<ms>(<pct>%)`）；关闭态不调 `Instant::now`（自测计数=0）。
- B 轮实测：**430/430** 条慢 tick 行都出现该项，均值 **1.451 ms**，占**工作段 2.34%**，范围 0.462–3.927 ms；
  同期 `HostInbound` 占工作段 82.8–84.5% ⇒ **它约占 `HostInbound` 的 3%**，不再是其主体。
- 原文样例：
  `SLOW tick#208 work=51.864ms ... HostInbound=42.941(82.8%) ... | probes hear_targets_at=1.079(2.1%)`
