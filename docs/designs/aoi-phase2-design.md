# AOI phase 2 设计：增量可见集维护（与差分等价验收）

> 目标读者：opc-07 复审。**不含实现**，只给设计、等价判据、测试计划、牙齿与风险。
> 入库位置：`docs/designs/aoi-phase2-design.md`（版本化，随分支提交）。

## 1. 现状与动机（用两轮遥测的数据说话）
- `output_aoi_system` 每 tick 遍历全部实体（`aoi_order.push`），但真正的窗口搜索
  `search_view_range_with_updates` 只按**每实体搜索间隔**触发（玩家 `search_time=1000ms`）。
- AOI 两轮实测：`cells_per_search≈621`、`cand_per_search≈672–1211`、`vis_per_search≈670–1210`、
  `ns_p50∈[131µs,262µs)`（线性桶后可直接读数）、`searches_per_tick≈326→712`。
  ⇒ 单次搜索在"几百格 / 上千候选里挑几十~几百可见"，**全量重扫的成本随在线人数线性上升**——
  这就是 phase 2（增量维护）的动机。
- 线性桶改造后，收益判据不再靠"2 的幂边界"，可给 `ns_avg` 与桶内分布。

## 2. 语义基线（必须**逐字节**保持）
增量实现必须复现 oracle/C# 与现有 Rust 行为的**全部可观测面**：
1. 每个观察者每 tick 的**可见集（有序）** [`visible_actors`]；
2. 每 tick 的**离开集（有序）**（`removed`，供"消失帧"与 `FixedHideMode/Ghost` 判定）；
3. 视野搜索的**触发时机**（`SearchTime` 门：玩家 1000 ms；其它类型沿用现值）；
4. `aoi_order`（实体遍历顺序）与 `by_grid`/`by_map` 分桶结果；
5. 搜索的**顺序语义**（x 外层 y 内层；已有测试 `aoi_scan_order_is_x_outer_y_inner` 盯住）。

**不允许**用"定期全量重扫兜底"来掩盖增量漏更新——那会把等价性测试变成假绿来源。

## 3. 增量设计（路线 A）
维护两类索引：
- `viewer_cells: viewer -> 其窗口覆盖的格子集合`（矩形，`(2R+1)^2` 格）；
- `cell_viewers: cell -> 覆写该格子的观察者集合`（与 `by_grid` 同寿命，随移动增量维护）。

触发面（只有三类会改变可见关系）：
1. **实体进入/离开某格**：更新该格 `by_grid`，对 `cell_viewers[cell]` 的所有观察者做增量
   （候选集变化：按可见性过滤后增删，保持顺序 = 扫描顺序）；
2. **观察者移动**：窗口矩形平移 ⇒ 计算差集（进入列/离开列），批量更新；
3. **观察者上下线/换图**：整窗插入/摘除。

每次触发仍然经过**同一套可见性过滤**（`FixedHideMode`/`Ghost`/存活状态），只是候选集来自
索引而不是全窗扫描。

## 4. 差分等价验收（核心）

### 4.0 骨架自证（两颗前置牙，opc-07 要求）
- **确定性牙**：同一实现（legacy）对同一输入序列**跑两遍**，每 tick 的有序可见集/离开集/`aoi_order`
  必须**逐项相等**；不等 ⇒ 说明实现内部存在非确定性（HashMap 迭代、并发），不得进入下一步。
- **检出力牙**：在双实现比较器里**故意在一侧丢弃一个可见实体**（测试夹具注入），差分必须报红。
  两条都要在报告里贴**输出原文**（绿的那次与红的那次）。

### 4.0a 比较器检查顺序（写死，保证"报第一条分歧"可复现）
```
SNAPSHOT_COUNT → TICK_VIEWER → 可见集（集合 → 顺序） → REMOVED → VIEW_UPDATES
```
**为什么 count 必须最先**：长度不等时 `zip` 会静默截断，先比集合会把"少了一整个快照"
错报成集合差异（牙齿用例 `a=36 b=35` 正是这么构造的）。顺序固定 ⇒ 同一对输入必报同一类分歧。
配套牙：`VISIBLE_SET / VISIBLE_ORDER / REMOVED / VIEW_UPDATES / SNAPSHOT_COUNT` 各一颗红，
外加**"少快照 + 内容也错"同时发生必须报 `SNAPSHOT_COUNT_MISMATCH`**（证明 count 优先不是靠顺序侥幸）。

### 4.0b 确定性来源（写死）
- 可见集与离开集**必须有序**；任何 `HashMap` 迭代必须先显式排序（或改用 `BTreeMap`/有序 `Vec`）。
- 差分比较器逐项比较顺序，并额外断言"同实现两次运行顺序完全一致"。

### 4.1 测试骨架
新增 `tests/parity/aoi_incremental_diff`：
- **同一输入序列**（脚本化：观察者移动、实体移动、上下线、换图、隐身/幽灵状态切换）；
- **同进程双实现**：`legacy_full_scan` 与 `incremental` 各跑一份状态副本；
- 每 tick 比较：`visible_actors`（**有序逐项**）、`removed`（有序逐项）、`aoi_order`、
  `by_grid` 桶集合；不一致 ⇒ 打印首个分歧 tick + 双方有序集合并失败。

### 4.2 覆盖矩阵（每项都要有专门用例）
| 类别 | 用例 |
| --- | --- |
| 实体进入格子 | 从窗外走进窗内；同 tick 多实体；边界格（正好 R 格） |
| 实体离开格子 | 走出窗外；被移除/死亡；换图 |
| 观察者移动 | 平移 1 格；跨图；快速连续移动（与搜索间隔交互） |
| 状态变化 | `FixedHideMode` 切换；Ghost 切换；隐身进出 |
| 上下线 | 观察者上线/下线；候选实体上线/下线 |
| 触发时机 | 搜索间隔门未到期时**不得**产生新的搜索（与现实现逐 tick 对齐） |

### 4.3 随机化 fuzz
固定种子 + 1000 步随机操作（移动/上下线/状态切换），每步差分断言；失败时打印种子与操作序列。


### 4.4 触发时点对齐（opc-07 要求）
增量必须在**与 legacy 完全相同的 tick 内时点**看到格子变化，否则差分会在慢速场景假绿：
- 先在测试里**固化 legacy 的时点**：写入移动/进入事件 → 同一 tick 内 `output_aoi_system` 观察到的
  `by_grid` 与实体位置，是"事件应用前"还是"应用后"；
- 用例覆盖：跨格发生在搜索间隔门**到期那一 tick** / **未到期 tick** 两种；
- 若 legacy 在 tick A 应用移动、tick B 才重扫（受 `SearchTime` 门），增量也必须在 tick B 才对可见集生效。

### 4.5 派生馈送（第一步口径）与集合对齐
- **不用事件注入，用派生馈送**：tick 边界保存 `id -> 格坐标` 快照（`BTreeMap`，列举顺序确定），
  与本 tick 结束值比对得出 `moved / entered / left`；完备性由构造保证，不依赖调用方"记得喂事件"。
- **集合对齐牙（前置，不过不谈等价）**：每 tick 比较 `snapshot.keys()` 与 legacy 扫描**实际遍历**的
  候选 id 集合，不等即报 `CANDIDATE_SET_MISMATCH tick=… snapshot_only=[…] legacy_only=[…]`。
  场景必须含 **Ghost** 与 **已死未清（store 已移除、格子里还在）**——这两类最易被"只收存活"漏掉。
- **`moved` 语义**：只记**跨格**；**格内微动不产生条目**（不触发观察者重扫）。
- **生产构建不含捕获分支**：universe 捕获与对齐断言全部 `#[cfg(test)]`；已用构建产物佐证——
  `CANDIDATE_SET_MISMATCH` / `AOI_ALIGN` / `AOI_MATRIX` 三个测试字样在 release `game-svr.exe` 中
  出现 **0** 次，在同源测试二进制中分别出现 2/1/2 次。
- **复杂度**：快照重建 `O(n log n)`（BTreeMap 插入）+ 比对 `O(n)`，每 tick 一次：
  4k 实体约 4k·12 ≈ 5 万次比较量级（微秒级），10k 约 2.5 倍；该开销归入 `idx_avg`，
  **不计入** `ns_*`（搜索段）。

## 5. 牙齿（缺一不可）
1. **删"实体进入格子"触发** ⇒ 差分用例必红（候选出现但可见集没更新）；
2. **删"实体离开格子"触发** ⇒ 消失帧/离开集用例红；
3. **删"观察者移动"触发** ⇒ 平移用例红；
4. **只删一个 arm**：三类触发各自独立删一次（防止"一条用例钉住 A 支、B 支没牙"）；
5. **顺序牙**：可见集顺序必须与扫描顺序一致（把增量结果排序化 ⇒ 顺序用例红）；
6. **空输入退化**：零实体/零观察者时行为与现实现一致（不得 panic、不得空转）。

> **牙的靶必须单独验证（2026-11-19 实测教训）**：「场景覆盖了触发类型」≠「每颗牙都有靶」。
> 窗口差分的「离开项」支最初拿 `viewer_moves` 当靶，但该场景里观察者右移时**没有实体离开窗口**
> ⇒ 删掉离开支仍全绿（假牙）。补了「观察者移走、怪留在旧窗口」的专测后，删支才红。同理，
> `entered`/`left` 两支第一版被状态指纹环与无条件的陈旧成员核对兜住，删掉也不红——后来把状态环
> 收窄为「两 tick 都在」、把陈旧核对限定在 `pruned_after_snapshot` 才让两支承重。**每条触发支
> 都必须有一条删掉就红的用例，且该用例要能证明自己被触发。**

## 6. 性能验收（与遥测同口径）
- 目标：4k AOI 段 p50 **≤150 ms**（达标 ≤100 ms）；10k **≤240 ms**（沿用容量预审口径）；
- 判读用 `ns_avg` + 线性桶分位（桶宽 32 µs 已入行），不再用 2 的幂边界；
- 对照方法：**同构建两轮**（开/关增量）× 相同参数，比较 AOI 段 p50/p90 与 `in_world/failed`
  （后者允许 ±2% 不劣化）。


### 6b 增量路径自身的仪器口径（opc-07 要求）
- `ns_avg`/分位只统计**搜索段**；增量实现里**索引维护**（`cell_viewers` 增删）的耗时**不计入**
  `ns_*`，但必须**单列**一个 `idx_avg`（同线性桶，桶宽同为 32 µs），否则"AOI 段变快"可能是把成本
  搬到了索引维护上；
- 报告同时给：AOI 段 p50/p90（`ns_*`）与索引段 p50/p90（`idx_*`），二者相加才是真实成本。


### 6c 内存（opc-07 要求，不设硬门槛但必须报）
- 双索引（`viewer_cells` + `cell_viewers`）相对 legacy 的 **RSS 增量**：4k 时 p50/p90；
- 报告口径：同一构建、同参数、`Get-Process WorkingSet` 每 10 s 采样；不设通过线，只作为取舍依据。

### 6d. 2026-11-19 4k 两轮实测：增量（初版）比 legacy 慢 37%，按实测重写

- 实测（同构建，只差 `MIR2_AOI_INCREMENTAL`）：tick 速率 3.51/s → 2.22/s；AOI 段
  `ns_avg` 340µs → 950µs（final 窗口）、`ns_p50` 416µs → 1,056µs；`inc_rate` 0.965，
  排除"回退太多"这条解释。
- 分段实测（本地 `tick_bench --profile --bots 4000 11000`，V≈171）：每趟 gate 30µs 中
  **`ordered` 全量收集 + `sort_by_key(scan_key)` 19µs（60%，`sort_by_key` 每次比较都重算
  两次 BTreeMap 查找）+ `view_updates` 逐目标 `store.get` 9µs（30%）**；legacy 同场景 21µs。
- 重写要点：可见成员表缓存（回退才重建）、移除用 `retain`、`view_updates` 只在「怪物 + 距离门
  内」的小集合上排序且**零 `store.get`**（字段全部来自 tick 快照）、`is_visible_active` 同源；
  tick 相容器换 `HashMap` 并合并为单表、双缓冲复用容量、`by_grid` 内层 `Vec` 复用。
- 遥测口径：增量路径不遍历格子 ⇒ `cells_per_search` 在行内标 `cells_sem=na`，
  `cand_per_search` 标 `cand_sem=touched`，并带 `mode=legacy|incremental`，禁止把 0 读成
  「省了 97%」。
- 剩余杠杆（未做，等重跑判读）：tick 相当前每实体仍做一次 `store.get`，`output_aoi_system`
  主循环也做一次；可预扫一次共用。

## 7. 风险与回退
- 风险①：顺序语义漂移（可见集顺序影响出帧）——用第 5 节顺序牙 + 有序差分盯住；
- 风险②：搜索间隔门与增量触发交互（间隔未到不应重算）——用例矩阵"触发时机"项；
- 风险③：边界格与视野半径定义不一致——用边界格用例 + 与 `search_view_range` 同源的窗口枚举函数；
- 回退：增量实现置于**同一模块的独立入口**（例如 `search_view_range_incremental`），
  由常量/开关选择；差分测试默认双跑；生产切换需一次同构建两轮对照。

## 8. 交付顺序
1. 差分测试骨架 + 覆盖矩阵（先红后绿：legacy 对 legacy 应全绿，证明骨架本身不假绿）；
2. 增量实现（cell_viewers + 三类触发）；
3. 牙齿逐条变异验证；
4. 性能两轮对照；
5. 合并与文档（含 oracle 偏差登记：若 oracle 也是全量扫描，本条属"实现优化不改语义"）。
