# D3 试验田报告：用 `bevy_ecs` 承载「掉落」系统（卡片 openmir2-d3-bevy-trial）

结论摘要：**该 ECS 方案与 parity 目标不冲突**（未发现"必须依赖 Query 迭代序"或"必须开并行"），
试验田的掉落系统与既有实现、与 C# 金标准三方一致；代价是**该子系统自身**比直接调用慢 ≈2.4×
（绝对值 +30µs/tick ≈ 200ms 预算的 0.015%）。这一点严格来说未满足 DoD ④ 的"不劣化"，**提请 owner 裁决**。

## 一、形态（DoD ①）

`crates/world-bevy`（**不重写** `crates/world`）：**纯函数式系统：输入快照 → 输出命令**。

| 面 | 实现 |
| --- | --- |
| 输入快照 | `DropSnapshot { seed, mon_random_add_value, catalog, monsters[] }`、`PlaceSnapshot { occupied[], drops[] }`（纯数据，不含任何 ECS 类型） |
| 输出命令 | `DropPlanOut { id, gold, items }`（= 既有实现的 `Entity.gold/drop_items`）、`FloorPlaceOut { map_id, x, y, obj_id }` |
| ECS 承载 | `World` + 组件 `MonsterId/DropTable/Atlas/DropBudget` + 资源 `RngRes/CatalogRes/OrderIndex/OutBudgets/ItemNumberRes` + 系统 `drop_budget_system` |
| 适配层 | `snapshot_from_world(&mir2_world::World, seed)`：只读既有实体索引拼快照 |
| 常驻形态 | `build_world(&snapshot)` + `plan_drops_in_world(&mut world, &snapshot)`（真实集成用；输出与"每次重建"逐项相同，有断言） |

## 二、四条硬约束怎么落实 + 怎么证伪

| 约束 | 落实 | 证伪方式（都实测） |
| --- | --- | --- |
| ① 单线程 executor | 显式 `schedule.set_executor(SingleThreadedExecutor::default())` | `no_parallel_guard` 正面断言源码里必须出现 `SingleThreadedExecutor` |
| ② 遍历顺序显式化 | 系统**不迭代任何 `Query`**：处理顺序来自 `OrderIndex`（**实体 id 升序**，与快照数组顺序无关）；按 `Entity` 取组件只用于取值 | `output_does_not_depend_on_query_order`：把同一批怪物**反序 spawn**（改变 ECS 内部顺序），输出必须逐项相同 ⇒ 一旦有人改回"迭代 Query"立刻红 |
| ③ 守卫升级 | 本 crate 自己的 `no_parallel_guard`：直接依赖白名单（只许 `bevy_ecs`/`bevy_app`/内部 crate）+ 源码扫描禁 `MultiThreadedExecutor`/`bevy_tasks`/`rayon`/`crossbeam`/`thread::spawn`；`crates/world` 的 `no_parallel.rs` 与 `World::tick` 线程断言**原样保留** | 扫描只看**代码**、跳过注释（第一版把文档里"禁止 MultiThreadedExecutor"的字样判成违规 → 已修，见"过程发现"） |
| ④ 原判据不降级 | `crates/world` 一行未改：14 实体×10 tick、session/drop 两个 golden 仍逐行一致；世界 tick P99 复测 447/1234/3093µs（m2b 447/1261/3233，噪声内） | 见"三、成本"的诚实结论 |

**⑤ 停下上报条款**：**未触发** —— 试验田用"显式索引 + 单线程 executor"就能满足 parity，不需要 Query 迭代序、也不需要并行。

## 三、对拍与成本（DoD ②③④）

```bash
cargo test -p mir2-world-bevy                                   # 试验田 4 条断言
cargo test -p mir2-parity-tests --test world_aoi_parity --test world_session_parity   # 既有对拍（不回归）
cargo run -p mir2-world-bevy --release --bin drop_bench         # 成本对比
```

- **② 与 C# 逐行一致**：`floor_placement_matches_csharp_golden` 断言 bevy 系统的落地命令
  **逐项等于** `tests/parity/world/golden/session.txt` 的 `floor` 行（该金标准由 C# oracle 的逐字拷贝产出）；
  `budget_matches_existing_implementation` 断言预算输出与 `crates/formula` 直接调用逐项相同（同种子同顺序）。
- **③ 不回归**：既有两个场景对拍全绿（crates/world 未改）。
- **④ 成本**（32 只怪/次，2000 次；`tests/parity/world/d3-drop-bench.txt`）：

| 路径 | P50 | P99 | max |
| --- | --- | --- | --- |
| bevy_ecs（含建 world） | 52µs | 105µs | 604µs |
| **bevy_ecs（常驻 world）** | **21µs** | **48µs** | 281µs |
| 既有实现（直接调用公式） | 11µs | 18µs | 44µs |

**诚实结论**：常驻形态下该子系统 ≈**2.4×** 直接调用（+30µs/tick）。相对 200ms tick 预算可忽略
（0.015%），但 DoD ④ 的字面判据（"P99 不劣化"）**未达标** ⇒ 交 owner 裁决：
(a) 接受（绝对值可忽略）；(b) 只把 ECS 用于"编排/状态"，公式仍留在 ECS 外（预期能把差距压到 ~1.2×）；
(c) 回退到 §4.2 既有实现。

## 四、版本与维护成本（须摆上台面）

- 本机可用版本是 **`bevy_ecs 0.19.1`**（设计文档 §4.2.2 写的是 0.20）⇒ 已按 `=0.19.1` **锁死**；
  升级需按"对拍基线即合同"的规矩单独评估。
- 依赖面：`bevy_ecs` 会引入 `bevy_tasks`（传递依赖，未启用并行使用）等一批 crate，
  编译时间与依赖面比"手搓 slotmap"明显更大。

## 五、过程发现（两条都会影响后续）

1. **守卫要扫代码、别扫文本**：第一版 `no_parallel_guard` 因为源码注释里写了"禁止 `MultiThreadedExecutor`"
   而误报 ⇒ 守卫必须过滤注释行（已修）。同理：任何"禁某 API"的文本扫描都要先剥注释与字符串。
2. **随机流是顺序敏感的**：第一版顺序无关性断言写成"每个怪物的结果不受插入序影响"，
   实测直接红（同一流按不同顺序消耗 ⇒ 结果不同）。这反过来**正面说明**了约束②的必要性：
   顺序一乱，与 C# 的逐行 diff 必破。断言已改为"打乱 spawn 顺序 ⇒ 输出完全一致（因为顺序来自我们的索引）"。
