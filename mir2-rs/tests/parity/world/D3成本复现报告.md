owner `openmir2-worker-9`，worktree `.claude/worktrees/dropbench`，分支 `worktree-bevy-dropbench`，

## 0. 结论

1. **缺口属实**：`cargo run -p mir2-world-bevy --release --bin drop_bench` 在重建前**无源码可跑**
   ——`crates/world-bevy` 下只有 `Cargo.toml` / `src/lib.rs` / `tests/bevy_drop_parity.rs`，
   `git log --all -- mir2-rs/crates/world-bevy/src/bin/drop_bench.rs` 为空。⇒ `D3试验田报告.md`
   的成本表与设计文档 §4.2.3 引用的数字**不可从仓库复现**。
2. **按验收 (a) 重建**：`src/bin/drop_bench.rs`（三条路径）+ `mir2-rs/.gitignore` 加 `!**/src/bin/`
   （根因与 `openmir2-m2-p99-bench` / `openmir2-verify-tools-bin-gitignore` 同一条：
   `**/bin/` 把 Rust 的 `src/bin/` 一起吞了）。
3. **三轮重跑同量级**（判据 ±50%）：P50 = **47 / 21 / 12 µs**（三轮 47/46/50、21/21/21、12/12/11），
   历史 = 52 / 21 / 11 µs（差 **−8% / 0% / +6%**）。
4. **但历史报告的"派生结论"不可复现**：`≈2.4×` 与 `+30µs/tick` **都不是它自己那张表能推出的**
   （表本身给的是 1.9× 与 +10µs/批）⇒ 已按可复现口径改写（§4）。
5. **本 bench 有分辨力**：`--redcheck`（"每只怪建一次 world"的错误用法）P50 = **835 µs**
   = 含建 world 的 **16.4×**，远超机器噪声。

## 1. 复现（写死口径）

```bash
cargo run -p mir2-world-bevy --release --bin drop_bench               # 三条路径 + 自检
cargo run -p mir2-world-bevy --release --bin drop_bench -- --redcheck  # 追加红检路径
```

场景（= `D3试验田报告.md` 表头"32 只怪/次，2000 次"；改一处基线即不可比）：
掉落表/目录 = `tests/bevy_drop_parity.rs` 那份（金币 300 + 金创药(小量)×1，`sel=9/max=10`）、
怪物 id 1..=32、固定种子 42、`MonRandomAddValue = 40`、每路径预热 100 次（不计入）、
百分位取最近秩 `s[ceil(p/100*n)-1]`、单位 µs。

**自检（本 bench 的牙齿之一）**：三条路径对同一快照的输出必须**逐项相同**，否则 exit 1
——即"测的必须是同一件事"。本轮 `gold=9248 items=32 make_index_sum=528`，三路径一致。

## 2. 结果

| 路径 | 本轮 P50/P99/max（三轮：run1、run2、run3） | 历史 `d3-drop-bench.txt` | P50 差 |
| --- | --- | --- | --- |
| bevy_ecs（含建 world） | 47/96/148、46/96/206、50/104/233 µs | 52/105/604 µs | −8% |
| bevy_ecs（常驻 world） | 21/40/74、21/42/60、21/40/63 µs | 21/48/281 µs | 0% |
| 既有实现（直接调用） | 12/20/28、12/18/19、11/15/99 µs | 11/18/44 µs | +6% |

原始输出：`d3-drop-bench-rebuild.txt`（入库）与 `E:\tmp\openmir2-bevy-dropbench\run{1,2,3}.txt`。
P50 三轮稳定（±5% 内），故"同量级"的判定以 P50 为准；P99/max 受当时机器负载影响（见 §5 口径注）。

## 3. 红检（可证伪）

同一工作量换成**每只怪建一次 world**（真实世界里"把 world 建在实体循环里"的写法）：

| 路径 | P50 | P90 | P99 | max |
| --- | --- | --- | --- | --- |
| bevy_ecs（含建 world，正确用法） | 51 | 87 | 106 | 215 |
| redcheck（每只怪建一次 world） | **835** | 1007 | 1475 | 1535 |

⇒ **16.4×**。即该命令能分辨"ECS 建 world 的频率"这类回归，不是噪声里看热闹。

## 4. 派生结论的更正（诚实项）

| 历史表述 | 可复现的实测 | 说明 |
| --- | --- | --- |
| 常驻 world ≈**2.4×** 直接调用 | **1.75×~1.91×**（三轮比值 1.75 / 1.75 / 1.91） | 历史表自身的两行是 21/11 = 1.9×，也推不出 2.4× |
| **+30µs/tick** | **+10µs / 32 只怪的掉落批次**（21µs − 11µs） | 单位的锅：C# `MonGetRandomItems`（`crates/formula/src/drop.rs` 头注释："创建怪物时预生成掉落"）在**怪物生成时**一次性预算，**不是每 tick** 跑一次 ⇒ 按 tick 表述会高估频率（32 只怪 / 11×9 的 AOI 窗口尺度下，一 tick 通常连一个新怪都没有） |

处置：

- `docs/Rust重写设计文档.md` §4.2.3 的规模实测句改为"**+10µs / 32 只怪的掉落批次（P50 21 vs 11µs，≈1.8×）**，
  命令与基线可跑"，并注明"掉落预算在怪物生成时一次性预算、不是每 tick"；
- `AGENTS.md` 的"D3 当前状态"段：补齐 owner 已接受（§4.2.3）与可复现数字，去掉过期的"待 owner 裁决"与 2.4×；

  并保留 owner 裁决记录原文。
