# 4) `SM_STRUCK` GAP 详情（本片**新**发现）

## 4a) 客户端要求的布局（从冻结客户端源码直接可得）

```
ClMain.pas:10238 SM_STRUCK:
  DecodeBuffer(body, @wl, SizeOf(TMessageBodyWL));      // 尾 = 16B {Param1,Param2,Tag1,Tag2}
  ...
  {$IF HIGHHP}
    Actor.m_Abil.HP    := DWORD(Makelong(msg.param, msg.tag));   // header 两格拼 32 位 HP
    Actor.m_Abil.MaxHP := DWORD(wl.lParam1);                     // MaxHP 在**尾** Param1
  {$ELSE}
    Actor.m_Abil.HP    := msg.param;
    Actor.m_Abil.MaxHP := msg.tag;
  {$IFEND}
```
⇒ 冻结客户端要的 SM_STRUCK = **header(actor, LoWord(HP), HiWord(HP), damage) + 尾{Param1=MaxHP, …}**；
而 C#/Rust 发的是 **header(actor, HP, MaxHP, damage) + 尾{Param1=feature, …}**（非 HIGHHP 口径）。
⇒ 客户端会算出 `HP = HP | (MaxHP<<16)`（一个虚高值）、`MaxHP = feature`（玩家 `GetFeature()` 值）。
受击**不伴随** 53（oracle 在 `RM_STRUCK` 支只发 `SM_STRUCK`，除 `DisableSelfStruck/DisableStruck` 两支），
故这个错值会**一直留在** `Actor.m_Abil.HP/MaxHP` 直到下一条 52/53/升级/换装覆盖 ⇒ 受击后 HUD 血条错乱。

## 4b) 与既有真机读数的自洽

既有 C# 对照组真机读数（`README.md` §结论 #3）：客户端 HUD `0/0` + `655360/25165829`
（`0xA0000 = 10<<16`、`0x1800005 = 24<<16 | 5`）——这正是「把 header 两格当 32 位拼」的形态，
与 HIGHHP 口径一致（片⑨/㊴ 的 52/53 归因同源）。⇒ 本 GAP 与 52/53 **不是**新缺陷类，是同一类的第三、四、五张牌。

## 4c) 为什么本片**不改**（交 owner）

1. **跨侧夹具冲突（硬阻塞）**：m3 ②③ 攻击夹具经 `src/BotSrv`（C#，**非 HIGHHP**）解 SM_STRUCK：
   `RobotPlayer.Operate.cs:682` 的 `Actor.Abil.HP = msg.Param; Actor.Abil.MaxHP = msg.Tag;` 与落盘
   `M3ATTSEQ {role=struck, "hp":msg.Param, "maxhp":msg.Tag, "src":wl.Tag1}`；`attack_diff.py` 按这两格做
   **跨侧逐 k 对拍**。若把 Rust 的 SM_STRUCK 改成客户端布局、C# 侧不动 ⇒ 夹具必红（本片若强改，会打断 ②③）。
   要修必须先裁决「夹具侧是否 pin `MIR2_CLIENT_ABILITY_LAYOUT=0`」或「C# 夹具同步改造」，**不在本片写集**。
2. **R 级**：SM_STRUCK 属战斗数值/客户端可见行为，真机两相（受击前后 HUD）判据归 root 独占窗口。
3. **§6.0-3 登记面**：52/53 的偏差登记（O-3）尚无 owner 签字；本 GAP 应**并入同一登记**一次裁决，
   不要逐帧各开一张（否则登记碎片化、且易与夹具口径打架）。
