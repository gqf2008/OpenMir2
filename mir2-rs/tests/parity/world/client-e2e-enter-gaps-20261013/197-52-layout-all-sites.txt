0. 为什么有这一片（承接 brief 顶块 DoD②「修 + 改坏必红」的**闭合**）
--------------------------------------------------------------------------------
片㊴（c61b9627a）修了 53 `SM_HEALTHSPELLCHANGED` 缺冻结客户端 `TCharDesc` 12B 尾；片㊴ 的
作者审计（卡内 comment，ts 1791969899）声称「52 生产默认 client-58 与客户端一致」。
本片**独立复核发现该结论不完整**：只有**入图**那条 52 走了布局开关，另两条生产出帧点
（升级 / 装备卸下）**无条件**发 oracle 40B `EncodeMessage(WAbil)`。

冻结客户端的 `SM_ABILITY` 处理器对**每一条** 52 都走同一个分支，按 `SizeOf(TAbility)` 整块解：

    Source/MirClient/ClMain.pas:10096-10102   DecodeBuffer(body, @m_Abil, SizeOf(TAbility))
    Source/Common/Grobal2.pas:39              HIGHHP = True  ⇒ TAbility 为 58B
    Source/Common/Grobal2.pas:2167-2193       TAbility: HP@22 / MP@26 / MaxHP@30 / MaxMP@34 (DWORD)
    Source/MirClient/Actor.pas:2162-2169      CanRun(): HP < RUN_MINHEALTH(10) ⇒ -1（拒跑）

40B 布局下客户端把 offset 22 读成 oracle 的 `Exp`（本部署 = 0）⇒ **HUD 0/0、CanRun 拒跑**。
⇒ 只要玩家**升级**或**换装**，客户端 HUD/跑门再次归零（与 root 在 verify2 观察到的
「52/752 不生效 + 跑=0」同一故障类），且会**烧掉 root 的 R 窗口**：窗口内若发生升级/换装，
已修好的入图 52 会被随后一条 40B 52 覆盖。

4. 与 oracle 的关系（§6.0-3 故意偏离，same switch as 52-58B / 53-TCharDesc）
--------------------------------------------------------------------------------
oracle 的 52 是 40B `EncodeMessage(WAbil)`（`PlayObject.Message.cs:1732-1735`）。oracle 的 40B
与冻结客户端的 58B **不可同时满足**；按硬约束 #1（客户端冻结）⇒ 默认以客户端为准
（`MIR2_CLIENT_ABILITY_LAYOUT` 缺省 = client-58；`=0` 回到 oracle-40 逐字节对拍）。
白名单登记（52 的 58B + 53 的 12B 尾）仍待 owner 签字（片㊴ 的 reviewer-5 O-1，随卡带走）。
