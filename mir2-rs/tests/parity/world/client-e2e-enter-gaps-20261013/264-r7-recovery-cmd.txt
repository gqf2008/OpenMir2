# 0) 一句话结论

R8 的 RED 自片63 起自带**可照抄**的停栈命令（`PREFLIGHT_STOP_CMD`），而 R7 的 RED 只有一句散文
「先重编译 + 重录清单」；同时 `client-e2e-window.fixed.sh.txt start` 在 `run_guard || exit 1` 处
**fail-closed 停住（不会替操作员编译）** ⇒ 一次 R7 RED（源前移且 `mir2-rs/**` 有生产差异、
或暖 target 里是别处拷来的旧件）就把开窗卡死，操作员只能回翻证据包。本片把 R7 的恢复动作
**可执行化**：工具打印 `PREFLIGHT_RECORD_CMD:`、替身脚本在 RED 时单独提取并印出该行、手册补 §1b。

# 1) 缺口（为什么这是开窗期的真缺陷，不是文案）

`check_rust_window_preflight.py` 的 R7（片㊻）在做一件 R6 做不到的事：证明 `<target-dir>/debug`
里的六件 exe **就是当前构建源编出来的**（R6 只比 git 差异）。它红起来只有两种原因：

  a. 清单 `source_head` != 当前 `--ref`，且两者在 `mir2-rs/bins|crates|Cargo.toml|Cargo.lock`
     上有差（真身 = **刷了源但没重编译**）；
  b. 某件 exe 的 sha256 != 清单（真身 = 暖 target 里是别处拷来的旧件 / 缺件）。

两种的正确恢复都一样：**重编译六件 + 重录清单**。但片63 只把 R8 的停栈命令做成了可照抄行，R7 没有；
且替身脚本的 `start` 顺序是 `run_guard || exit 1` → `cargo build`（即 RED 时**拒绝走到编译那步**）。
⇒ 操作员必须**手工**拿到确切命令。

反证（本片实拍，§3.2）：拿修复前 ref `8e491f81e` 跑真门，R1/R6/R7 都 RED，但 base 版的输出里
**没有**任何可照抄的 R7 恢复命令（`grep -c PREFLIGHT_RECORD_CMD` = 0）—— R8 那条有
（`PREFLIGHT_STOP_CMD`），R7 这条没有。

**fail-closed 要点（本片最要紧的一条）**：`--record-provenance` 只是把**当前** `--ref` 盖到清单上，
它**不校验** exe 是否真由该 ref 编出（这是该子命令的信任边界）⇒ 「编译失败也录制」会把旧件洗成新源、
R7 随即**假绿**。故命令用 `&&` 串联：`cargo build` 非零 ⇒ 整条链短路、清单保持原样、R7 继续 RED。
该性质有独立牙：`r7-record-cmd-gated-on-build-success`（断言 `cargo build` 必须出现在
`--record-provenance` **之前**，且两者之间是 `&&`）。

# 4) 恢复命令形态（工具实际打印的那一行）

```

  -p game-svr -p game-gate -p login-srv -p login-gate -p sel-gate -p db-srv && \
  python -I -B "<证据目录>/check_rust_window_preflight.py" --repo "<源>" --ref HEAD \
    --target-dir "<target-dir>" --record-provenance "<target-dir>/window-provenance.json"
```

- 路径加双引号以容忍空格；`--ref HEAD` 与窗口口径一致（不引入新的 ref 语义）。
