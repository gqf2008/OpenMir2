# M2 ④ 复测前置：`tick_bench` 重建与 P99 基线复现

卡片：`openmir2-m2-p99-bench`（owner `openmir2-worker-7`，分支 `worktree-m2b-p99`）。日期：2026-10-11。

## 0. 结论

1. **缺口是真的**：M2 DoD ④ 与设计文档 §4.2.3 引用的 `tick_bench` **从未进入 git**——根因是
   `mir2-rs/.gitignore:3` 的 `**/bin/`（本意是 C#/MSBuild 的构建输出）把 Rust 源文件惯例目录
   `src/bin/` 一起吞了。`git check-ignore -v` 可以一行复现。
2. **已修**：`.gitignore` 加 `!**/src/bin/` 负向规则（目录必须自身被重新包含，git 才继续往里看）；
   `tick_bench` 入库并给出可复现的三档 P50/P90/P99/max。
3. **门禁有牙齿**：把 `EntityStore` 的 `id → 槽位` 索引临时换成线性扫，同一命令的 P99 变成
   **2877 / 12975 / 72947 µs**（= 索引版的 5.0× / 10.9× / 25.0×）。
4. **口径要认账**：历史两份 `p99-baseline*.txt` 没有生成器，其 P50 明显高于本次重建
   （421/435 vs 377；1122/1261 vs 840；2937/3099 vs 1783），**无法对账**（见 §3）。
   从本报告起，④ 的"不劣化"以**本报告口径**为准（场景写死在 bin 头注释 + §2），
   历史的 `p99-baseline.txt` / `p99-baseline-m2b.txt` 降级为历史对照。

## 2. 复现（写死口径）

```bash
cargo run -p mir2-world --release --bin tick_bench -- 500 2000 1000 2000 2000 1000
```

场景（= `M2骨架报告.md:45-46` 写死的口径，改一处基线即不可比）：

- 200×200 地图（`World::new(200, 200)`）；
- 实体铺在奇数坐标、相邻 **2 格**（`x = 1 + 2*(i%100)`、`y = 1 + 2*(i/100)`）；
- 固定种子 42（`World::with_maps` 内部即 42）；
- 每 tick 让 `i % 4 == tick % 4` 的 1/4 实体走一步，方向每 4 tick 翻转（在 2 格带内来回，不撞边界）；
- 首 tick 只做"入图"（`add_entity` 的 Enter 队列一次性落图），**作为预热不计入样本**；
- 百分位取最近秩 `s[ceil(p/100*len)-1]`。

读法：**P50 跨轮稳定（±1%）**，P99 跨轮抖动约 ±20%（tier-2000 最明显）⇒ 回归判定先比 P50，
P99 要看三轮中位数，不要拿单轮 P99 的小差别当回归。

历史文件的 P50 高出本次 12%~65%（tier 越大差越多），**超出噪声范围**，说明旧 bench 的每 tick
工作量比本重建更大（最可能是实体密度的差异——原文"间隔 2 格"指坐标步长还是"空 1 格"已不可考）。
因为旧生成器从未入库，这一差异无法对账，也不该用"本次更便宜"去宣称"旧基线被改善"。

## 5. 判定口径（给 M2 ④ / M5，按 owner 裁决 `5e1daee` 校准）

1. 跑 §2 的命令三次（`--baseline` 模式由工具自己对每档跑 3 轮），取各档 P50 与 P99 的**中位数**；
2. 与 `p99-baseline-tickbench.txt` 对比：P50 劣化 > 10% 或 P99 中位数劣化 > 30% ⇒ 判回归；
3. **绝对 P99 ≤ 100ms 只在空载窗口才有意义**：它是 M5 的验收目标，不是并行环境下的每次合并门禁——
   `--baseline` 模式下只作为报告值打印（含时间戳与负载），不参与退出码；不给 `--baseline` 时行为与历史
   完全一致（1 轮、只判绝对 100ms、超了 `exit 1`）。

> **已机判化（2026-10-11 初版，同日按 owner 裁决返工）**：
>
> ```bash
> cargo run -p mir2-world --release --bin tick_bench -- \
>   --baseline mir2-rs/tests/parity/world/p99-baseline-tickbench.txt 500 2000 1000 2000 2000 1000
> ```
>
> - **只判相对量**：每档 3 轮取 P50/P99 中位数，`P50 > +10%` 或 `P99 中位数 > +30%` ⇒ `RED` / `exit 1`；
>   轮次**跨档交错**（先各档第 1 轮、再回头第 2 轮……），不再"先把一档跑满"。
> - **绝对 P99 降级为报告值**：只打印（含时间戳与负载），不影响退出码。
> - **负载守卫**：若 CPU ≥ 50% 或 `rustc`/`cargo`/`cargo-clippy`/`msbuild` ≥ 4 个（前后两次探针取峰值），
>   相对量不可信 ⇒ 打印 `SKIP-UNDER-LOAD` 并 `exit 0`——**不把负载导致的 RED 当作者的锅**。
>   但**数量级**劣化（P50 > +150% 或 P99 中位数 > +400%）不是负载能解释的，负载下仍判 `RED`（保住牙齿）。
> - 缺档 ⇒ `SKIP`（不静默当通过）；读文件失败 ⇒ `RED`。

### 5.1 为什么不是"同进程内交替跑 baseline 与 candidate"

owner 裁决 `5e1daee` 第 1 条的字面要求是"同一进程内**交替**跑 baseline 与 candidate（A/B/A/B…）"。
在本卡语境下**无法照字面落地**，原因是结构性的，不是实现懒惰：

- `--baseline` 的 A 侧是**静态数字文件**（`p99-baseline-tickbench.txt` 只有 P50/P99 列），没有可执行的
  基线版本；要"在同一进程里重测 baseline"就必须先把基线代码编进同一个二进制；
- 本卡写集只允许动 `tick_bench.rs`（禁改 `crates/world` 其它面、禁加第二个可执行文件），
  **没有承载"基线实现"的位置**；把同一份代码测两遍得到的 A/B 恒等，不构成对照；
- 真正的交替 A/B 在本项目里是**跨构建**做的（如 wbevy S1/S2：`master` 与 head 各编一个 `tick_bench.exe`，
  由脚本 A/B/A/B 交替跑，证据 `E:\tmp\openmir2-wbevy-s2\ab*.txt`）——那需要两次构建与一个 runner，
  超出本卡"机判 `--baseline`"的范围。

因此按裁决的**可接受退路**（`required_implementation` 第 5 条 / F2 建议）落地：**门禁只判相对量 +
高负载 ⇒ `SKIP-UNDER-LOAD` 且 `exit 0`**，并用"数量级劣化"阈值保住负载下的牙齿。跨构建的交替 A/B
仍是 ④ 的推荐手工口径（见 §5.2 的实测）。

### 5.2 负载下的实测（阳性 / 阴性对照，2026-10-11）

命令与 §5 的机判工具相同，tiers = 500/1000/2000。当时机器常驻多条 agent 车道（`node.exe` 等），
CPU 负载 11%~71%。

- **阴性（未改任何源码）**：连跑 5 次 ⇒ **5/5 `exit 0`**：4 次 `SKIP-UNDER-LOAD`（探针 57%~62%），
  1 次在负载回落到探针 40%/3 进程时判 `GREEN`（ΔP50 +1.6%~+2.2%、ΔP99 +8%~+24%）。
  原始输出 `E:\tmp\openmir2-tickbench-gate\rework\negative-load-reruns.txt`。
- **阳性（`EntityStore::get` 换线性扫，跑完 `git checkout --` 还原，sha256 前后都是 `4edc0f91…`）**：
  即使探针处于高负载（CPU 59%），三档仍全部 `RED` / `exit 1`：P50 劣化 **+574% / +1689% / +3592%**；
  同批**绝对** P99 = 3696/17575/73183µs 全部 < 100ms ⇒ 只看绝对量会假绿。
  原始输出 `E:\tmp\openmir2-tickbench-gate\rework\positive-linearscan.txt`。
