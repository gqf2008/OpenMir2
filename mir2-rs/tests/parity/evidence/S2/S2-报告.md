## 2. 判定：夹具数据 vs 生产路径

### 2.1 暴露面（扫真实语料 639 个 `.txt`，原始输出 `probe-sweep-envir.txt`）

| 指标 | 数 |
| --- | --- |
| 条件命令行总数 | **1433** |
| 派发被位移掉的行数（B-8 位移面） | **1433（100%）** |
| 落到 `ConditionOfCheckRangeMonCount` 的行数 | **120** |
| 其中 `sParam5` 不足 2 字符（**必抛**）的行数 | **120（全部）** |

120 行完整清单已落 `crash-corpus-120.txt`（制表符分隔：相对路径 + 脚本文本），可直接当 B-8 修复批次的回归语料。
出现位置：`Market_Def/沙巴克铁匠-3.txt`、`Npc_Def/比奇国王-0122.txt`、`Npc_Def/勋章-0146.txt` 等。

**结论**：这不是"某条夹具数据写歪了"，而是一个**结构性**问题——真实内容里 120 条同形状的行都会抛。

### 2.2 该处理器在现网**没有任何合法调用**

全语料 `CHECKRANGEMONCOUNT` 命中数 = **0**。也就是说：这个处理器**只会**被位移误入的行调到
（`CHECKITEMADDVALUE` 那 120 行）。这一条对 §3 的取舍很关键。

### 2.3 夹具的玩家状态与本崩溃无关

崩溃点在**读任何玩家/世界状态之前**（第 1112 行早于 `GetVarValue`、`MapMgr.FindMap`、`monList` 统计）。
因此用例里的 `gold=100000`、`items/player_items=祈福项链/祝福油` 都不影响结果——
换任何初始状态都一样抛。「夹具数据不合规」这个假设不成立。

### 2.4 生产可达性 + 被谁兜住

- **可达**：`Npcs.txt` 第 3 行 `比奇国王　1　0122　29　32　0　8`，第二列 `type=1`
  → `LocalDB.LoadNpcs` 的 `switch` 走 `case 1: npc = new GuildOfficial()`（`src/GameSrv/DB/LocalDB.cs:688-693`）。
  该 NPC 的 `[@main]`（脚本第 1 行）在 `checkitem 祈福项链 1` 通过后就会显示
  `<复原[祈福项链]/@rw03>`（脚本第 38 行）—— 玩家点它即进 `[@rw03]` 的第一个 `#IF`。
- **被兜住**：`GuildOfficial.UserSelect`（`src/GameSrv/Npc/GuildOfficial.cs:55`）把
  `M2Share.ScriptEngine.GotoLable(...)`（同文件 :66）**放在 try 里**，`catch (Exception ex) { LogService.Error(ex); }`（:112-115）。
  异常在那层被吞掉并记日志 ⇒ **GameSvr 不崩、NPC 不倒**，玩家侧表现 = 该选项**无响应**。
- 另两个脚本 NPC 类是同一写法：`Merchant.UserSelect`（`src/GameSrv/Npc/Merchant.cs:807` GotoLable 在 try 内、
  :944 catch）、`CastleOfficial.UserSelect`（:98 try / GotoLable :115 在 try 内）⇒ **三类脚本 NPC 都兜得住**。
- **未审计的面**（如实声明）：全仓 `GotoLable` 调用点 123 处，其余（如 `Robots/RobotObject.cs` 的挂机脚本）
  的包含性本批**没有逐点审计**；本崩溃的触发语料全部是 NPC 脚本行，故上面的结论对本次用例成立。

### 2.5 为什么 B 线看到的是"崩溃"

B 线的对拍工具 `mir2-rs/tools/script-parity-cs` 直接调脚本求值，**没有生产 NPC 层的 catch**，
所以异常从工具里逃逸、进程带 EX 退出；而生产里同一异常被 `UserSelect` 吞掉。
**两者的差异是"包含性"，不是"行为"**——这正是这条用例没法直接当判据的原因（§3.1）。

## 3. 处置建议

### 3.1 建议：登记豁免 + 归 B-8 修复批次（本批不动 `src/`）

理由（按项目自己的规则）：

1. **根因是 B-8 位移**，而 B-8 在 `whitelist.md` 里已明确登记为"复刻的 C# 已知 bug，修复另立批次"。
   在**唯一受影响的那个处理器**上加长度守卫，是表象修复（`RULE_修复规范`：修根因不修表象）。
2. **行为等价优先于修 bug**（设计文档 §1 硬约束 3）：Rust 侧复刻的是"按 accept 序/位移派发"的旧行为，
   C# 单点加守卫会让 oracle 偏离这份复刻基线，B 线必须再追一轮 Rust 改动来对齐一个**玩家看不见**的差异。
3. **改与不改的玩家可见结果很可能相同**：现状是"异常 → 被吞 → 选项无响应"；
   加守卫后该处理器会走到 `ScriptConditionError` → `success=false` → 同样无响应（只多一条脚本错误日志）。
   既然可见结果相同，就不值得现在动 oracle。
4. **B-8 修复后本崩溃自动消失**：位移修好之后 `CHECKITEMADDVALUE` 回到它自己的处理器
   （那里有正常的参数校验），这 120 行不再误入。

给 B 线的具体建议：
- **登记豁免**：该用例不能作为"两侧效果逐行一致"的判据；豁免依据就是本报告（C# 侧在该 `#IF` 上必抛，
  且抛点在读玩家状态之前 ⇒ 与用例的 gold/items 无关）。
- 若希望这条用例仍可比：把对拍工具的输出**按生产的包含性**处理——即工具层也捕获求值异常，
  并把它作为一行可比的效果输出（例如 `COND_THROW IndexOutOfRangeException ConditionOfCheckRangeMonCount`），
  Rust 侧同样输出。这样两侧都"能跑完"，差异才可判。
- 把这 120 行（`crash-corpus-120.txt`）纳入 B-8 修复批次的回归语料：修好后应能看到
  `CHECKITEMADDVALUE` 派发回 `ConditionOfCheckItemAddValue`。

### 3.2 若协调者要求"立即修"：最小改法与代价（本批**未**实施）

最小改法只有一处（约 4 行）：在该处理器入口对 `sParam5` 做长度校验，不足 2 字符就走既有的
`ScriptConditionError(normNpc, baseObject, questConditionInfo, ConditionCode.CHECKRANGEMONCOUNT); return;`。

代价与影响（供拍板）：
- 属 oracle 行为变更 ⇒ 按 S1 纪律要 `whitelist T-4` + 改前后记录 + 重跑 M0/M1 + Rust 侧同改（否则不等价）。
- 受影响面：仅这 120 行位移误入的调用（该命令在现网真实调用数为 0）⇒ 不会动到任何合法行为。
- 但它**不会**让 B 线那条用例直接变绿：Rust 侧还要同步"位移派发 + 该守卫"两条，才能两侧一致。
- 收益仅为"把一条被吞的异常换成一条明确的脚本错误日志"。**建议不做**，等 B-8 批次一起收。

## 5. 工具健壮性两条（已修 + 已验）

### 5.1 现象

`tools/oracle/verify_gate_reconnect.ps1` 与 `deploy_gamesvr.ps1` 在用户侧跑完后 **stdout 不回、会话不退**
（产物齐全）。

### 5.2 根因（实测）

PowerShell 5.1 的 `Start-Process -RedirectStandardOutput/-RedirectStandardError` 用
`CreateProcess(bInheritHandles=true)` 起子进程，子进程会**把父脚本的 stdout/stderr 管道句柄一起复制过去**
（只多一份句柄，不改它自己的 stdout，所以日志照旧进文件）。只要子进程活着，调用方就读不到 EOF ——
脚本自己的工作早已做完，于是表现为"跑完了却不回"；服务端是长命进程 ⇒ 等于永远卡住。

分形状测量（子进程故意活 12 s；原始输出 `tools-pipe-ab.txt`）：

| 形状 | 调用方读到 EOF 的耗时 |
| --- | --- |
| 改前：`Start-Process` + PowerShell 级重定向 | **11 464 ms**（= 子进程寿命）✗ |
| 改后：.NET `ProcessStartInfo{UseShellExecute=$true}` + cmd 内重定向 | **342 ms** ✓ |

真实脚本（改前一次、改后各一次）：

| 脚本 | 改前 | 改后 |
| --- | --- | --- |
| `deploy_gamesvr.ps1`（`| cat`） | 工作全部做完但 `cat` 读不到 EOF，45 s 被 `timeout` 杀掉（rc=124） | **6 925 ms 全流程走完并正常返回**（`tools-deploy-after.txt`） |
| `verify_gate_reconnect.ps1`（`| cat`） | 同上（GameGate 是长命进程） | **55 093 ms 全流程走完并正常返回**，且本次判据 5 GREEN / 0 RED（`tools-gate-after.txt`） |

### 5.3 改法

新增 `tools/oracle/detached.ps1`：`Start-DetachedProcess` 用
`.NET ProcessStartInfo{ FileName='cmd.exe', UseShellExecute=$true }` 起服务
（ShellExecuteEx 路径**不继承**任何句柄），把 `> out 2> err` 写进 **cmd 自己解析的那段命令行**，
日志照样落文件；另附 `Stop-ProcessTree`（`taskkill /T /F`）——流程用完连子进程树一起收，
避免留下的孩子占句柄。两个脚本的长命服务启动点都改走它。

**已知边界（做成响亮失败）**：该命令行形式要过 cmd 一层引号解析，路径带空格时不可靠
（实测：可执行路径与日志路径都带空格时**会静默起不来**）。本仓库部署路径（`E:\MirServer\...`）不含空格；
`Start-DetachedProcess` 一旦发现路径含空格就**直接 throw**，绝不让调用方拿到"看起来成功其实没起"的结果。
（这也正是本轮踩到的坑：早先一个"看起来能用"的写法其实没启动进程，被我当成"已修"。）
