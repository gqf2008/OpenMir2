## 二、阻塞 2（判据）：`scoped_diff.py diff` 目前不是有效判据（本批新发现）

### 2.1 现象：两次都判 GREEN 的 C# 侧运行，互相 diff 却判 RED

```
命令： python mir2-rs/tests/parity/m3/scoped_diff.py diff \
         sessions/csharp-20261010-164731/scoped_after_norm.jsonl \
         sessions/csharp-20261011-110827/scoped_after_norm.jsonl
输出： DIFF mir2_account.account: rows A=1 B=1 仅A=1 仅B=1
       DIFF mir2_account.account_protection: rows A=1 B=1 仅A=1 仅B=1
       DIFF mir2_db.characters: rows A=1 B=1 仅A=1 仅B=1
       DIFF mir2_db.characters_indexes: rows A=1 B=1 仅A=1 仅B=1
       RED: 作用域内 8 行不一致
退出码： 1
```

两次运行各自都过门禁（各自 `M3-gate-csharp-*.json` 均 pass=true）；把其中任一次换成 Rust 侧，
结论一模一样是 RED。⇒ 跨侧 diff 现在**只会恒红**，与 Rust 行为无关；M3 的「diff = 0」判据
在这种状态下一旦被当成结论，就是**假红**（反向的假绿：有人可能把它当"已知噪声"登记掉，从而放过真差异）。

### 2.2 根因：`scoped_diff.py diff` 对**整行** `row_sha256` 比对，而行里含随运行变化的列

`row_sha256` 覆盖 `SELECT *` 的全列（`cmd_diff` 比 `row_sha256` 集合）。实测逐列差异（A=2026-10-10 会话，B=2026-10-11 会话）：

| 表 | 差异列（0-based） | 列名 | 差异示例 | 性质 |
| --- | --- | --- | --- | --- |
| `mir2_account.account` | 0 | `Id`（自增 PK） | 6344 → 11403 | 每次运行必变 |
| | 5,6,9 | 3 个 datetime | `2026-10-10 08:47:42` → `2026-10-11 03:08:38` | 墙钟 |
| | 11,12,13 | 3 个 unix 秒 | `1791622062` → `1791688118` | 墙钟 |
| `mir2_account.account_protection` | 0 | `AccountId`（= account.Id） | 6344 → 11403 | 自增外键 |
| `mir2_db.characters` | 0 | `Id`（自增 PK） | 12234 → 13239 | 每次运行必变 |
| | **11** | **`Job`** | **1 → 0** | **夹具自身随机**（见 2.3） |
| | 40,41 | `CREATEDATE` / `LASTUPDATE` | 跨天 | 墙钟 |
| `mir2_db.characters_indexes` | 0 | `Id`（自增 PK） | 12237 → 13242 | 每次运行必变 |
| | 5,6 | 2 个 datetime | 跨天 | 墙钟 |

其中「自增 Id / AccountId / 时间戳」是可预期的"生产端口径"，但**`Job` 是夹具自身的随机**，
连"字段语义相同"都不成立：

### 2.3 根因（更硬的一条）：假人建角时 **职业随机**，两侧根本不是同一个输入

`src/BotSrv/Scenes/Scene/SelectChrScene.cs:154-176`（只读取证，红线段未改）：

```csharp
byte sHair = 0;
switch (RandomNumber.GetInstance().Random(1)) { ... }   // :157 发颜色随机
byte sJob  = (byte)RandomNumber.GetInstance().Random(2); // :174 职业随机 (0/1)
byte sSex  = (byte)RandomNumber.GetInstance().Random(1); // :175 性别随机
SendNewChr(RobotClient.LoginId, sChrName, sHair, sJob, sSex);
```

`RandomNumber.GetInstance()` 内部是 `new Random()`（无种子，时间驱动；`src/OpenMir2/RandomNumber.cs:20-38`）
⇒ **每次运行的建角输入不同**。跨侧对拍的前提是"同序列"，而这一格从一开始就不是同序列，
拿它做 diff 只能得到噪声。

### 2.4 影响与建议（**本批不自行改判据**，留给 owner 拍板）

`scoped_diff.py` / `run_pair.ps1` 是 D2 卡经 owner 决策**提升为正式门禁**的判据本体
（`README.md` 首段）。改它等于改正式判据，属设计决策，不应由首验卡静默完成。建议二选一（或组合）：

- **方案 A（推荐，夹具侧、不碰 oracle）**：给 `scoped_diff.py diff` 增加**字段级规范化/白名单**：
  ① 忽略自增 PK 与 FK（`Id` / `AccountId`）；② datetime / unix 秒列以列名识别后置占位；
  ③ `characters.Job/Hair/Sex` 置占位（输入随机，非法作为行为判据），把这 3 列的行为对拍
  移到"固定 Job 的单测/独立场景"（例如 Rust 侧单测钉 `CM_NEWCHR→DB` 的落库值）。
  规范化后必须**保留改坏必红**的自检（补一例：改动被比对列的值必须判红）。
- **方案 B（更彻底但要动工具）**：让 BotSrv 的建角参数可配（固定 Job/Hair/Sex），
  使"同序列"真的成立。这属于 `src/**` 工具改动，需另开卡并按 src 冻结纪律评审。

在 A/B 落地前，本卡的「字段级 diff = 0」判据**不可用**。
