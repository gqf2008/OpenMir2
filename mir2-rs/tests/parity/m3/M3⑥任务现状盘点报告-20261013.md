## 0. 一句话结论

**「任务」在本 oracle 里不是一张任务日志/状态机表，而是「NPC 对话脚本 + 角色 `QuestFlag` 位数组」这条链；
脚本层（M4）与角色侧任务数组（M2）都已就位，缺的是「服务端触发/派发 + 会话任务态 + 帧」这条生产链，
而 `落库` 在 oracle MySQL 里本身就是空实现（要如实对齐「不落库」）。**

- **脚本层（M4，已收口）**：`{Quest N}` / `#IF [flag] = value` / `#RAND` 任务脚本选择门（`ScriptEngine.cs:146-168`、
  `ScriptParsers.cs:790-823`）、条件 `CHECK`（`ConditionProcessingSys.cs:4174`）、动作 `SET/RESET/SETOPEN/SETUNIT/RESETUNIT`
  （`ExecutionProcessingSys.cs:2036-2071`）都已在 `crates/script` 与 C# 逐行对齐；M4 用例 `任务-Q001@main` 是**脚本体**用例。
- **角色侧任务数组（M2 record-fields，已收口）**：`QuestFlag` / `QuestUnit` / `QuestUnitOpen`（各 `byte[128]` 位数组）
  已作为 `CharacterData` 的 52 成员之一被 Rust 解码/重编码（`playerdata.rs:669-671`、`record.rs:508-510`）。
- **缺件（本卡 DoD②③ 的真缺口）**：`crates/envir` 无 `MapQuest.txt`/`QManage`/`QFunction`/`RobotManage` 加载器；
  `bins/game-svr` **不依赖 `mir2-script`**（脚本运行时未接线）、**无 `@Login` 触发**、无 NPC 对话 `SM_MERCHANTSAY` 发送路径
  （与 ⑤ 的「服务端 NPC/商人派发面整个缺件」同源）；`bins/db-srv` 与 oracle MySQL 一样**不持久任务态**。
- **oracle 里三条「看似任务」的死路径**（要连 bug 一起搬，不是缺口）：`MapQuest.txt` 的怪/物品触发
  （`GetQuestNpc` 调用点被注释，`PlayObject.cs:1670/1677`）、`SendQuestMsg`（唯一调用点在注释里，`StartQuestCommand.cs:22`）、
  `QuestDiary`（解析结果丢弃，`LocalDB.cs:804`）；`Mission`（`BaseObject.Mission`）是**怪物集火目标**，不是玩家任务日志。

⇒ 本卡 DoD②③（接/交/条件判定 + 任务状态落库真机对拍）在承接卡补齐前跑不出可判原始件；本片只交 DoD①，
**未起栈、未占端口、零 `.rs`**。

## 4. 判据设计草案（DoD②）与夹具可复用性（DoD③ 口径）

### 4.1 §6 原文判据（不放宽）

> 「任务：用现存脚本任务跑：**接 / 交 / 条件判定一致，任务状态落库一致**。」

拆成四条机判：

1. **接/交/条件判定一致**：同一起点 + 同一 label 序列（例 `任务-3 @rw06` → `@06rw` → `首饰店-5 @main`
   → `@rw02` → `书店-0 @rw03`）下，两侧给出的**说词帧序列**（`SM_MERCHANTSAY` 文本逐字节）+ **金币/背包/装备**
   变化逐项相同（复用 ①/⑤ 的 `SM_*` 帧与 `characters`/`characters_bagitem` 作用域）。
2. **会话任务态一致**：每次动作后两侧的 `CharData.Quest*[128]`（`QuestFlag`/`QuestUnit`/`QuestUnitOpen`）
   逐字节相同（例：`set [107] 1` ⇒ `QuestFlag[13] & 32 != 0`）。这是本卡与 ⑤/① 的最大区别点，
   必须**显式导出会话任务态**（Rust 侧 dump / C# 侧同一记录），不能只看帧。
3. **落库一致（= oracle 的「不落库」）**：任务交互后两侧 DB 快照 `scoped_diff --canonical` 在
   `characters_quest`（已在作用域、`PLAYERID` 归属）**行数与字段 diff = 0 且两侧均 0 行**，
   `characters` 无任务列变更。⚠️ **必须把口径写成「两侧都不持久」**，不许写成「任务标志跨重登保留」——
   oracle MySQL 本身不保留（§1.F）。若后续要实现「真持久」，那是**规格变更**，要 owner 签字另立卡。
4. **fail-closed**：缺文件/缺字段/非法 JSON/k 不连续/两侧帧序列长度不同/任务态导出缺失 ⇒ 非零退出并点名；
   改坏任一侧任一字段（帧文本、任务态一位、DB 一行）⇒ 必红。

### 4.3 夹具可复用性（**能复用 `run_pair.ps1` 两相 pin + `scoped_diff`**）

调查原件见 [`03-fixture-reuse-survey.txt`](evidence-m3-quest-inventory-20261013/03-fixture-reuse-survey.txt)。

- **`-PinStartPose`（预热建角 → SQL pin → BEFORE 快照 → 计分跑）直接可用**：接/交要求玩家贴 NPC；
  真实数据候选位点：`任务NPC/任务-3.txt` 的 NPC（`MerChant.txt` 对应项）；`苍月岛` 首饰店/`比奇城` 书店同理。
  与 ⑤ 的 pin 机制相同（`run_pair.ps1:57`/`:111-115`）；`run_pair.ps1` 的 pin（`PinMapName/PinCX/PinCY/PinLevel`）
  可复用；任务无需 R-1 的「整图零刷怪」隔离（判据不是 RNG 逐 k）。
- **DB 判据可复用 `scoped_diff.py`**：`characters_quest` **已在 `TABLES` 作用域**（`scoped_diff.py:98`）并已登记
  `FAMILY_TABLES`（`"mir2_db.characters_quest": "PLAYERID"`，`:115`）；`--canonical` 的易变列白名单与
  `run_pair.ps1` 的 BEFORE/AFTER 快照 + `delta` 直接覆盖「落库一致」（第 3 条）。
- **需要新增的只有**：① BotSrv 的「任务动作序列」（现只有 `-BagEquipSequence`/`-AttackSequence`，
  `RobotPlayer.cs:421/653`；**BotSrv 无 `CM_CLICKNPC`**，`ClientGetMerchantSay`（`RobotPlayer.cs:4131`）是空壳）；
  ② 比较器 `quest_diff.py`（帧序列 + 任务态 + `scoped_diff` 组合）；③ 夹具入口 `run_quest_pair.ps1`
  （薄封装 `run_pair.ps1` + 标签序列参数 + 自检）。三者都是 **m3bag 写集**，需 owner 派。
- **前置阻塞**：任务 NPC 与 `@Login` 只在**服务端把脚本引擎/MapQuest 加载接起来**后才存在（承接卡 1/3）；
  在那之前夹具点不到任何任务 NPC。这也是「本卡 DoD②③ 跑不出原始件」的直接原因。

### 4.4 必须处理的「状态/时序」坑（写进夹具设计，否则 flaky）

1. **任务态不落库**：不要把「重登后标志仍在」当判据（会假红）；两条路线：
   (a) 全程同一会话内比较（会话任务态 + 帧）；(b) 明确把「重登后重置」也纳入判据（两侧都重置才算绿）。
   **优先 (a)**，与 oracle MySQL 行为一致。
2. **`@Login` 会自动跑一批脚本**（真实 `QManage.txt` 的 `[@Login]` 调 `#CALL` 月卡/代练等），
   会给任务态/背包/金币带来**非本用例**副作用 ⇒ pin 后必须 `settle` 到 `@Login` 完成，或选一个
   `@Login` 副作用最小/为空的语料（fixture 需在 README 写清选了哪个脚本、为什么）。
3. **`CHECK` 的 flag 从 1 起**（`nFlag -= 1`；`flag 107` ⇒ 索引 13、bit 32），夹具导出任务态时按 `byte[128]` 原样比，
   不要提前做「人类可读 flag→bit」映射（否则两侧各自实现易分叉）。
