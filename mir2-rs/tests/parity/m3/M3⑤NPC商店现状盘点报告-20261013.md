## 0. 一句话结论

**脚本层已就绪（`crates/script` 能解析商人脚本头 + `[goods]` 并用 M4 7/7 钉住）；服务端派发面整个缺件。**
oracle 的买/卖/修理/仓库是「收包 → `FindMerchant` → `UserSelect`/`Client*Item` → 价格公式 + 金币/背包/负重/库存
副作用 → `SM_*` 帧 → 存档落 DB」一条链；Rust 侧

- `crates/data` 有 `StdItem`（含 `Price`/`Weight`/`DuraMax`/`StdMode`）✅，
- `crates/script` 能解析 `MerChant.txt` 指向的商人脚本（`(@buy @sell @repair …)` 头、`%PRICERATE`、`+StdMode`、`[goods]`）✅，
- 但 `crates/envir` **无 NPC/商人加载器**、`crates/world` **无 NPC/商人实体**、`bins/game-svr` **不派发任何
  `CM_MERCHANTDLGSELECT`/`CM_USERBUYITEM`/… 且无价格/库存/仓库会话态** ❌。

⇒ 本卡 DoD②③（价格与库存变化一致 + 失败分支一致、真机两侧对拍）在承接卡补齐前**跑不出可判原始件**；
本片只交 DoD①（盘点 + 证据 + 设计草案），**未起栈、未占端口、零 `.rs`**。

## 4. 判据设计草案（DoD②）与夹具可复用性（DoD③ 口径）

### 4.1 §6 原文判据（不放宽）

> 「买 / 卖 / 修理 / 仓库的**价格与库存变化一致**；**钱不够、负重满等失败分支也要一致**。」

拆成四条机判：

1. **价格一致**：同一起点 + 同一序列下，两侧对每一击操作给出的价格（`SM_SENDGOODSLIST` 的价目、
   `SM_SENDBUYPRICE`、`SM_SENDREPAIRCOST`）逐字段相同。
2. **库存/金币变化一致**：每次操作后，玩家 `Gold`/`ItemList`（含 `MakeIndex/Dura/DuraMax`）与商人
   `GoodsList`（组内件数 + 顺序）逐项相同（DB 作用域字段级 diff = 0）。
3. **失败分支一致**：每个失败用例的**帧种类 + 参数**相同（`RM_BUYITEM_FAIL` 的 `n1C` 在 2/3 之间不能混；
   `SM_STORAGE_FULL` vs `SM_STORAGE_FAIL` vs `SM_TAKEBACKSTORAGEITEM_FULLBAG` vs
   `SM_TAKEBACKSTORAGEITEM_FAIL` 不能互相顶替），且**无帧分支**（`ClientRepairItem` 不支持 / 仓库未解锁的
   静默 return）也要判「确实无帧」。
4. **fail-closed**：缺文件/缺字段/非法 JSON/k 不连续/两侧帧序列长度不同 ⇒ 非零退出并点名；改坏任一侧任一字段 ⇒ 必红。

### 4.2 记录 schema 草案（每行一次交互，`npc_shop_raw.jsonl`）

```json
{
  "k": 0,
  "npc": "仓库保管员", "npc_actor": 1234, "map": "0145",
  "op": "storage",                  // buy | sell | repair | query_sell_price | query_repair_cost | storage | takeback
  "req": {"item": "金条", "make_index": 42, "n": 1},
  "frames": [{"sm": 704, "a": 1234, "b": 0, "c": 0, "d": 0}],
  "gold_before": 1000, "gold_after": 900,
  "bag_before": ["金条#42"], "bag_after": [],
  "storage_before": [], "storage_after": ["金条#42"],
  "goods_before": [{"name": "金条", "count": 1}], "goods_after": [{"name": "金条", "count": 2}],
  "price": 100,
  "branch": "ok"                    // ok | fail_nomoney | fail_overweight | fail_bagfull | fail_no_frame | fail_storage_full | ...
}
```

必填 `k/npc/op/frames/gold_*`，按 `op` 增补对应 `*_before/after` 与 `price/branch`；`k` 从 0 连续。

### 4.3 夹具可复用性（**能复用 `run_pair.ps1` 的两相固定起点口径**）

调查原件见 [`03-fixture-reuse-survey.txt`](evidence-m3-npc-shop-inventory-20261013/03-fixture-reuse-survey.txt)。

- **`-PinStartPose`（预热建角 → SQL pin → BEFORE 快照 → 计分跑）直接可用**：商店交互要求玩家贴 NPC
  （`<=15`/`IsWithinSight`），pin 正是把玩家钉到「NPC 旁固定格」的既有机制。
  - 候选位点（真实数据）：仓库 `0145 (9,12)` → pin 玩家到 `(9,11)`；修理 `d2008 (31,24)` → pin `(31,23)`；
    买/卖 `0103 (19,18)` → pin `(19,17)`。
- **DB 判据可复用 `scoped_diff.py`**：买/卖/修理/存取都只动 `characters`（Gold/背包）+ `characters_storageitem`
  的行，作用域内字段级 diff = 0 即 §4.1 第 2 条。`run_pair.ps1` 的 BEFORE/AFTER 快照 + `delta` 已经覆盖。
- **同侧可重复性前置**（同种子连跑两次逐字段一致）可照抄 M3②③ 的会话口径；但 **NPC/商店判据不是 RNG 逐 k**
  （§6 原文只要求价格/库存/失败分支一致），所以**不需要**隔离 RNG 专用流；R-1 的
  `Test-M3MonGenEmpty`/`Test-M3MapNoAiConsumers` 也**不适用**（本场景不含刷怪/掉落）。
- **需要新增的只有**：① BotSrv 的「NPC/商店动作序列」（现有 `-BagEquipSequence`/`-AttackSequence` 是模板，
  但不含选 NPC / 开面板 / 买 / 卖 / 修理 / 存取）；② 比较器 `npc_shop_diff.py`；③ 夹具入口
  `run_npc_shop_pair.ps1`（薄封装 `run_pair.ps1` + 序列参数 + 自检）。三者都是 **m3bag 写集**，需 owner 派。

### 4.4 必须处理的两个「状态/时序」坑（写进夹具设计，否则 flaky）

1. **商人货架依赖墙钟**：`GoodsList` 初始为空，`RefillGoods()` 只在 `Run()` 的 **5 分钟门**后触发
   （`Merchant.cs:122`），且商品**不落盘**（§1.B）。⇒ 夹具两条可行路线（**不许**改 oracle）：
   - (a) **卖后回购**：先 `CM_USERSELLITEM` 把玩家一件 `Dura>0` 物品卖给商人（`AddItemToGoodsList` 进 `GoodsList`），
     再用 `CM_USERBUYITEM` 买回 —— 货架由**夹具自己造**，确定且不依赖 5 分钟门；**优先**。
   - (b) 若必须用脚本 `[goods]` 商品，则每次运行须在起栈后 **settle ≥ 5 分钟**（并保证整段交互 < 下一个补货点），
     成本高、时间窗口敏感，作为备选。
2. **`ClientUserBuyItem` 与 `IsWithinSight` 的距离口径不一致**（真实 quirk，必须连 bug 一起搬）：
   前者用 `|dx|>15 || |dy|>15` 拒（即 `<=15` 放行，`Operate.cs:200`），后者用 `<15`（`Operate.cs:1715`）。
   ⇒ pin 距离取 **14** 可让两侧都稳定通过；若要打这条边界（dx=15），要作为**边界用例**单列并登记。
