## 0. 结论摘要（先看这里）

1. **范围 6 个魔号**：`2 SKILL_HEALLING`（治愈术）、`29 SKILL_BIGHEALLING`（群体治疗术）、
   `23 SKILL_FIREBOOM`（爆裂火焰）、`24 SKILL_LIGHTFLOWER`（地狱雷光）、`33 SKILL_SNOWWIND`（冰咆哮）、
   `47 SKILL_47`（地狱烈焰）。oracle case 区间分别 `204-224`、`443-449`、`418-423`、`424-430`、`489-494`、`595-600`。
2. **取数**：六个魔号的效果体在**施法者侧**都恰为 **4 抽**
   （`MPow` → `GetPower` → `GetAttackPower` 内 `Random(nPower+1)` → `R(10)`），唯一例外是
   **2 的 `IsProperFriend` 门失败 ⇒ 0 抽**（`MagicManager.cs:211` 把整段 `:213` 包住）。
   `GetPower`/`GetAttackPower` 的 `R(0)` **照样推进**（魔表多数 `Power==MaxPower`、`DefPower==DefMaxPower`）。
3. **交付侧另有抽数**：`RM_MAGSTRUCK` 到目标后，怪物目标（`Race>=Animal && !RushMode &&
   WAbil.Level<50`）先抽 `Random(1000)`（`BaseObject.Base.cs:620-623`），再抽
   `GetMagStruckDamage` 的 **1 抽**（`:624` → `:814`）；若 `nDamage>0` 且目标是玩家，
   `PlayObject.StruckDamage` 再抽 `R(10)` + 每个非空装备格 `R(8)`（`PlayObject.cs:2957`、`:3000`）；
   若目标是怪物，`AnimalObject.Struck` 还会在 `TargetCret` 非 null 且 `GetAttackDir` 失败时抽 `R(6)`
   （`AnimalObject.cs:342`）、`Animal=true` 时抽 `R(300)`（`:352`）。`nDamage==0` 时后面整条链不执行。
   计划件「29/23/24/33/47 固定 4 抽」只对**施法者侧**成立，见 §5-C2。
   `RM_MAGHEALING` 交付**0 抽**（只累加 `IncHealing`）。
4. **帧**：共享尾的 `RM_MAGICFIRE(10120)` 六个魔号都发（`boSpellFire` 恒 true）；
   `boSpellFail` 六个都恒 false（无护身符门），所以 B2 没有 case 内 639。
   639 只可能来自既有包装层（MP 不足 / 距离门 / 版本门）。
   23/24/33/47 的每个受击怪物（`nDamage>0`）还会产生一条 `SM_CHANGENAMECOLOR(656)`（§2.3(c)）。
5. **`boTrain`**：2 = `HP < MaxHP` 且 `IsProperFriend`；29 = 3×3 内任一友方回血；
   23/33/47 = `MagBigExplosion` 任一 `IsProperTarget`；24 = `MagElecBlizzard` 任一 `IsProperTarget`。
   六者都不改 `boSpellFire`/`boSpellFail`。
6. **B2 不读 `AntiMagic`/`AntiPoison`**（不走 `MagCanHitTarget`、没有 `R(10) >= AntiMagic` 骰门）。
   唯一防御向读数是目标 `WAbil.MAC`（交付侧 `GetMagStruckDamage`）。`Entity` 目前**没有 MAC 字段**
   ⇒ 这是 B2 的硬前置（§6-1）。
7. **本件相对计划件的关键订正**（§5）：
   - `RM_ABILSEEHEALGAUGE` 的 SM 收件人是**施法者**，不是治疗目标（C1）；
   - 23/24/33/47 的交付抽数必须进账（C2）；
   - 24 的 AoE 中心是**施法者坐标**，共享尾坐标仍是点击/ snap 坐标（C5）；
   - 死亡目标在 2 上会把治疗对象改写为施法者并改写尾帧坐标（C7）；
   - `AP` 第三抽是 `Random(nPower+1)`（`nPower` = `GetAttackPower` 第二实参）：2/29 传 `nPower=(Hi(SC)-Lo(SC))*2+1=17` ⇒ `R(18)`、23/24/33/47 传 `nPower=Hi(MC)-Lo(MC)+1=11` ⇒ `R(12)`（旧稿 `R(17)`/`R(11)` 错，C15）；
   - 交付段漏了怪物 `R(1000)` / `R(6)` / `R(300)` 抽（C16）；
   - 受击怪物自消息会产生 `SM_CHANGENAMECOLOR(656)`，不是「无客户端帧」（C17）；
   - `PerHealing=5` 只在 `IncHealing+n<300` 分支内（C18）；治疗目标恢复期每 tick 一条 53。

### 1.6 帧序的隐藏变量：`MsgQueue` 优先级（**必须写进实现注释**）

oracle 的立即消息不是按调用顺序上线，而是入每个对象自己的
`PriorityQueue<SendMessage, byte>`（`ActorEntity.cs:16`）。`SendMsg` /
`SendRefMsg` 的优先级 = `(byte)wIdent`（`BaseObject.Message.cs:94`、`:181`），
`SendSelfDelayMsg` 一律 `MessagePriority.Lowest = 255`（`MessagePriority.cs:8`、`BaseObject.Message.cs:204`）。
`PriorityQueue` 按**数值升序**出队 ⇒ 帧序由低字节决定：

| ident | 常量 | `(byte)` 优先级 |
|---|---|---|
| `RM_SPELL(10008)` | 17 | 24 |
| `RM_HEALTHSPELLCHANGED(10052)` | 53 | 68 |
| `RM_STRUCK(8018)` | 31 | 82 |
| `RM_MAGSTRUCK(8044)` | —（目标侧处理，无直接 SM） | 108 |
| `RM_MAGICFIRE(10120)` | 638 | 136 |
| `RM_CHANGENAMECOLOR(8090)` | 656 | 154 |
| `RM_MAGIC_LVEXP(10123)` | 640 | 139（但经 `SendSelfDelayMsg` ⇒ 255） |
| `RM_STRUCK_MAG(8103)` | 31 | 167 |
| `RM_ABILSEEHEALGAUGE(10414)` | 1103 | 174 |
| `RM_MAGHEALING(8034)` | —（延迟） | 255 |

推论（B2 必读）：
- 施法者队列：`53(68)` → `638(136)` → `1103(174)`；**`1103` 在 `638` 之后**，
  尽管 `MagicManager.cs:221` 的 `SendMsg` 在 `:648` 之前调用。
- 被治疗目标队列：`17(24)` → `638(136)` → `RM_MAGHEALING(255, 800ms)` → 恢复 tick 的 `53`。
- 受击玩家队列：`17(24)` → `RM_MAGSTRUCK(108)`（处理时产生 `53(68)` 与 `31(167)`）→
  `53(68)` → `638(136)` → `31(167)`。
- 受击怪物/观察者队列：`638(136)` → `656(154)`（怪物自消息链 `RM_STRUCK`→`BreakHolySeizeMode`
  →`RefNameColor`，每条命中的怪物一条）→ `31(167)`。
- 同优先级的多个帧（29 的多条 `1103`、多个受击者的 `31`）出队次序由 .NET 堆实现决定，
  **不是插入序**；R 级判据若要求逐帧序，必须先在真机窗口抓一次 oracle 的实际顺序，
  或只断言「同优先级集合 + 不同优先级相对序」。
- 本仓现有实现多数**直接发帧**、不建模该优先队列（已有多处登记）⇒ B2 若沿用直接发帧，
  必须按上表**人工按优先级重排**；否则 `53 → 1103 → 638` 这类顺序会与 oracle 相反。

## 6. 未决项 / 硬前置 / 自失效声明

### 6.1 硬前置（未落地前 B2 不得进 R 级验收）

1. **目标 `MAC` 注入面**（23/24/33/47 的交付抽）：`Entity` 无 `mac`；现有
   `combat::struck_damage_durability` 只覆盖 `STD`，没有 `GetMagStruckDamage`。
   需要：目标 `MAC` 的可读面（扩 `Entity` 属 `crates/world` 接口变更，须通知并行车道；
   或沿用「宿主传值」先例按目标 id 传入），以及 `combat::get_mag_struck_damage(rng, target_mac, n_power)`。
2. **`RM_MAGSTRUCK` 交付处理器**：需要把 `RM_MAGSTRUCK` 入目标队列 → 怪物先抽 `R(1000)` →
   抽 `MSD` → `if (nDamage>0)`：扣 HP / `HealthSpellChanged`（53）/ `SendRefMsg(RM_STRUCK_MAG)`（31）/
   怪物自消息（`R(6)`/`R(300)` + `SM_CHANGENAMECOLOR(656)`）。
   现有 `drain_combat_downlink` 只处理 `rec.attacks`（物理攻击），不覆盖魔法伤害。
3. **有序目标枚举** `World::mag_objects_in_range(map_id, x, y, range)`（P3-3），
   顺序 = x→y→格内插入序；过滤 `!Death && !Ghost`。不能沿用 `EntityStore::iter` 槽位序。
4. **延迟队列载荷扩展**（P3-2）：`slave::SelfDelayMsg` 只有 `actor_id/ident/deliver_at_ms`；
   B2 至少需要 `wParam/nParam1`（`RM_MAGHEALING` 的 `nPower`）与 `UpdateDelayMsg` 的
   `(ident,nParam1)` 去重语义（640）。
5. **`AbilSeeHealGauge` 宿主字段**：`SessionGround` 无该字段；`RM_ABILSEEHEALGAUGE` 的生产者需要它。
6. **`Invisible` 折叠裁决**（C13）：oracle 的 AoE 会命中 invisible 目标（枚举只滤 Death/Ghost，
   `IsProperTarget` 不读 `Invisible`）。若要保留 Rust 的折叠，必须在卡片登记偏差并让夹具避开
   invisible 目标；否则 B2 的「命中集合」判据会与 oracle 不同。

### 6.2 其他未决

- **`SetTargetCreat` 的副作用**：oracle `MagBigExplosion` 对每个 proper target 调
  `SetTargetCreat`（`MagicManager.cs:1110`），改的是**施法者（`baseObject`）**的 `TargetCret`
  （实现为 `this.TargetCret = 参数`，`BaseObject.Base.cs:557-561`），**不是目标的 `TargetCret`**；
  B2 目前只把它当「无帧」。跨批（B4/B5）若读施法者的 `TargetCret`，这里必须建模。
  登记为「B2 不建模、跨批再评估」。
- **`MagBigExplosion` 的 `objectList.Clear()`**（`MagicManager.cs:1115`）：只是释放，无行为差异。
- **怪物目标的 `RM_STRUCK` 自消息**：`BaseObject.Base.cs:672-679` 在 `Race > Play` 时还会
  `SendMsg(RM_STRUCK, …)`；该消息由 `AnimalObject.Operate`（`AnimalObject.cs:118-133`）处理，
  做 `SetLastHiter`/`Struck`（AI 仇恨）与 `BreakHolySeizeMode`；`Struck` 会抽 `R(6)`（条件）与
  `R(300)`（`Animal=true`，`AnimalObject.cs:342`/`:352`），`BreakHolySeizeMode` → `RefNameColor`
  → `RM_CHANGENAMECOLOR(8090)`，观察者收到 `SM_CHANGENAMECOLOR(656)`（`PlayObject.Message.cs:1677-1678`）。
  ⇒ **帧面判据必须包含 656**；若做 AI 行为对拍，还必须保留 `SetLastHiter`/`Struck` 的副作用。
- **`MonDelHptoExp`**：缺省 false（`GameSvrConf.cs:1832`）。若开启，`BaseObject.Base.cs:630-671`
  会在每次怪物命中后再调 `GetMagStruckDamage`，额外消耗一次 `R(|Hi(MAC)-Lo(MAC)|+1)`；
  夹具必须 pin false（或把它写进交付账本）。
- **`nDamage==0`**：`BaseObject.Base.cs:625-680` 整段（StruckDamage/53/31/自消息/656）只在
  `nDamage>0` 时执行；33/47 的高 MAC 组合可能把伤害降到 0，夹具需用零伤害变体覆盖（§2.3(f)）。
- **`M2Share.RandomNumber` 的 .NET 版本**：生产 `new Random()` 在 .NET 6+ 是 xoshiro256**，
  固定种子 legacy 才是可对拍序列；本件全部按 legacy（与仓内 `mir2_shared::rng` 同口径）。
